# Journeys

How Lowdefy's config tests (journeys) are built in code: the grammar, selection, the runner, data sets, app errors, traces and session logs, production evidence and tiers, hardening, and pull request scope. What a journey does for an app developer, and every command option, is in the user docs under `packages/docs/testing/`: `config-tests.md`, `journey-data-sets.md` and `explore-pull-request.md`. This page names where each piece lives and the rules that are not visible from those docs. How to run the framework's own journey suites is in [testing.md](../testing.md).

The designs behind it are in Pelican, under the LDF-133 (Journey loop) project.

## The grammar

One grammar, in `node-utils/src/journeyGrammar/`. Everything that checks a step imports it, so the CLI, the dev server's runner, `screenshotPage`, the journey REST route, lint and variants agree.

- `validateJourneySteps.js` exports `validateJourneySteps`, `STEP_KEYS`, `TARGET_KEYS`, `INTERACTION_STEP_KEYS` and `getStepKey`. Interaction steps are click, open, fill, select, press and back. `expect.error` and `expect.effect` must directly follow one (`validatePlacement`); `expect.error` may instead read the answer of a `call`, `request`, `release` or `webhook` step, and `expect.status` must, with only expect steps between them. A `release` names the `requestId` of a `hold` before it, as a string or as `{ requestId, endpoint?, pageId? }` that fits one of the holds (`validateReleasePlacement`).
- `journeyStepSchema.js` holds the same grammar as JSON Schema (`journeyStepSchema`, `JOURNEY_STEP_SCHEMAS`). The dev server serves it through `lowdefy_get_schema` with `kind: "journey-step"` (`server-dev/lib/docs/getSchema.js`).
- `journeyStepExamples.js` ends every step error with an `Example: ...` line, and the schema carries the same examples.
- `validateJourneyStub.js` checks one entry of a journey's `stubs`: an answer `{ connectionType, requestType, answer, requestId?, endpoint?, pageId?, match? }` or a forced failure `{ requestId, endpoint?, pageId?, fail, times? }`. `validateJourneyStubs.js` checks the list, for lowdefy test's `validateJourney`, the journey route and `lowdefy_run_journey`. `journeyStubSchema.js` is the same as JSON Schema for agents; its tests keep the two agreeing.
- `validateJourneyDataSession.js` refuses `stubs`, `hold`, `release` and `expect.sunk` on a journey with no `data`, since they live on the data session: `validateJourney` and the dev server's `runJourney` and `runJourneyHeadless` call it, so every host refuses alike, whether or not it would open a session.
- `findJourneyPlaceholder.js` finds a `_case` or `_ref` left in a journey, which would be sent as a literal object. `validateJourney` runs it after refs are read and rows filled in, over every value, since a file's `_case` fills anywhere. The journey route and `lowdefy_run_journey` run it with `literal: true` on what they are sent (`findSentPlaceholder`): only the places a file's placeholder stands for part of the journey are checked (a step, a step list, a stub or the stub list, `user`, `data`, `pageId`, and `pathParams` and `urlQuery` or one of their values), and one inside a value is data, as a page-less payload may carry operator objects. A sent journey with a `cases` key is refused outright: it would run once with each `_case` sent as written. `lowdefy_run_journey` takes `cases` in its schema only to refuse it, since the MCP SDK drops keys its schema leaves out.
- `normaliseJourneySteps.js` expands shorthands (`wait: 3000` becomes `{ wait: { ms: 3000 } }`). `runJourney` and `screenshotPage` call it after validation.
- `validateJourneyTags.js` (`JOURNEY_TAG_PATTERN`, the data set name pattern) and `validateJourneyUser.js` check `tags` and `user`. `findPlaceholderStep.js` finds a `from: shape` placeholder. `normaliseBlockId.js` turns list indices into `$`.

The CLI checks a journey file in `cli/src/commands/test/validateJourney.js`: the ajv shape check from `journeySchema.js` (a closed root: an unknown top-level key is refused, naming it and listing the keys; step keys from `STEP_KEYS`, `name` at most 100 characters, `description` at most 60 words, `cases` from `casesSchema.js`, `serial` a boolean), then `evidence.mutation` (killed at most total), then `stubs` (each entry through `validateJourneyStub`; `stubs` without `data` is refused, since stubs live on the data session), then `validateJourneyUser`, `validateJourneyTags` and `validateJourneySteps`. A journey with `cases` has its root keys checked first, so an unknown key names the journey rather than a row, and is then validated once per run, after its row is filled in. A malformed file is an invalid result before any server starts (`checkJourneyItem`), and the run's other journeys go on. Nothing in discovery or expansion adds a root key: `expandedFrom` lives on the item, and a variant (`buildVariantJourney`) copies only schema keys, `serial`, `stubs` and `cases` included. `serial: true` marks a journey that must run with no other journey in flight; the run pool reads it (see "Running journeys side by side"). The name limit applies to the name as written, never to a persona run's `<name> [<user>]`.

## Selecting journeys

`lowdefy test` and the `lowdefy_run_tests` agent tool (`cli/src/commands/mcp/runAppTests.js`) share one selection in `cli/src/commands/test/`:

1. `parseTestSelection` reads paths, tags, filters, tier and usage window.
2. `resolveJourneyPaths` turns paths into files. With no paths, `discoverJourneys` reads `tests/journeys/` through `listJourneyFiles` with `skipUnderscored`. Reading a file resolves every `_ref` in it (`resolveJourneyRefs`, `readJourneyRef`) from the config root, as a build does: only `_ref: <path>` and `_ref: { path }` to a `.yaml`, `.yml` or `.json` file; `vars`, `key`, resolvers, transformers and `.njk` are refused, a `_ref` with keys beside it is refused, and a referred file may refer on. The chain of files on the way is held by real path (`fs.realpathSync`), so a ref through a symlink is still seen as a loop. A loop, a missing file or a refused form makes the file one error item, as invalid YAML does. Shared files live under `tests/shared/`, since every file under `tests/journeys/` is read as a journey. A named folder is read whole, `_` folders included. A path that does not exist and contains `*`, `?` or `[` is expanded with `fs.globSync`, so npm scripts on Windows behave the same. A glob matching nothing, a path outside the config directory, or a glob matching only non-journey files is refused.
3. `selectTests` applies tags and filters (each repeatable, any match counts; paths, tags and filters combine with AND) and expands user lists and case tables into runs (`expandJourney`).
4. `selectTier` (async) cuts the tier over that selection and returns `deprecated: true` journeys as skipped. `--lint` returns before it, so lint ignores `--tier`.
5. `formatNoTestsMatched` explains an empty selection.

The two differ in what they give back. `lowdefy test` prints every journey's lines. `lowdefy_run_tests` answers an agent, and a client refuses an answer it cannot hold, so `runAppTests` cuts it with `compactTestResults.js`: `summary`, `failed` (each failing or flaky journey with its report and failure), `passed` and `skipped` (one line per journey) and `resultFile`. The lists hold at most 20,000 characters as printed. Failures keep their full detail for the first 12,000, are then named with a message cut at 300 characters, and passing lines take what is left; `omitted` counts what did not fit (`failedDetail`, `failed`, `passed`, `skipped`). Every journey of the run, with its report, is written to `.lowdefy/test/results.json` (`writeTestResults.js`), which `resultFile` names. A journey's `exercised` path is in neither: it runs to thousands of entries a journey, and `exercised.json` keeps it (see "Hardening").

The shim sends one MCP progress notification per finished journey (`createProgressSender.js`) when the client passed a progress token with the call, so a long run is not silent.

The MCP tool resolves `paths` against the config directory, the CLI against the current directory. The MCP tool always reads `tests/journeys/`; `--journeys-directory` is CLI only.

`isFullSuiteRun` is true only for a run with no paths, filters or tags, tier `full`, and only for its first repetition. Only such a run records `journey` traces and `.lowdefy/test/run.json`. Skipping deprecated journeys keeps a run whole.

## Running journeys side by side

`runJourneyPool` (`cli/src/commands/test/runJourneyPool.js`) runs the selection for all three runners: `lowdefy test` on the dev server, `runAppTests` (`lowdefy_run_tests`) and `runHeadlessTests` (`--headless --build`). Each item is still one `runRepeated` call. The pool keeps up to `readLimit()` items in flight and returns the results in selection order, so `summariseResults`, `compactTestResults`, `writeTestResults`, `writeExercised`, `writeTestRun` and `writeHeadlessRun` read the same list as before; `browserOnly` results are split out of it afterwards.

- **Which items overlap.** An item whose journey names a data set (`data`) runs beside others: `openDataSession` gives it databases of its own. An item with no `data`, with `serial: true`, or repeating the `file#name` of an item before it runs alone, with nothing else in flight. The repeat rule matters for a recorded run, whose error buffer is keyed by the run and `file#name` (`runErrorBuffers.js`). The overlapping group runs first, then the alone group one by one, each in selection order.
- **The limit.** `readJourneyConcurrency` gives a browser run's `readLimit`: `--concurrency`, `concurrency` or `LOWDEFY_JOURNEY_CONCURRENCY` (an empty value is unset), each 1 to 3 (the browser slots), else 1. It is 1 with `--repeat` above 1, and 1 while `readMemoryPressure()` (`commands/hub/`) reports `warn` or `critical`, read each time the pool would start a journey beside one in flight. There is no load-average rule: agent sessions keep a laptop's load above its core count for hours. Headless runs pass `() => 1` (decision `parallel-browser-runs-only`): dev-server headless runs in the dev server's one thread, and `--headless --build` shares one test app. `readHeadlessMode` refuses a typed `--concurrency` beside `--headless`, `readAccessMode` beside `--access`, and `runAppTests` a `concurrency` beside `headless`; a `concurrency` from `lowdefy.yaml`'s `cli` config is left alone. `journeys harden` and `journeys variants` keep their own loops.
- **Output.** `onReported` prints an item once it and every item before it in run order have finished, so an alone journey early in the selection never holds the rest back, and the `seen` set that prints a data set's notes once stays deterministic. `onFinished` fires as each item finishes; `runAppTests` sends it as MCP progress (`done` counts finished items, `total` is fixed). A run function that throws fails that item (`class: 'FAIL'`, its message, and its `stack` when it has one), and the run goes on. Such a throw is a runner bug rather than a journey's, so `results.json` keeps the stack and `formatJourneyResult` prints it once per run, under the first journey it failed (`seen`), and `stack: as printed above` under the rest.
- **A contended failure is rerun alone** (decision `contended-failure-rerun-alone`). An item that fails while another item's run call was executing (`attempt` marks both when one starts beside another) is run again once, alone, before it is reported, whatever the limit is by then: memory pressure or an earlier alone pass may have brought it to 1 while the item ran beside another. A result that is `refused`, `stale` or `browserOnly` would come back the same alone and is reported at once; a page-open timeout or a slot wait that ran out (`{ message }`, no `failure`) and a thrown run function count. The pool starts nothing new while a rerun waits, waits until no run call is executing, then calls `run(entry, { rerun: true })`; two contended failures rerun one after the other. The callers pass no `recording` on a rerun, since recording again would append a second attempt under the same run id and `file#name`. Passing alone, the item is `PASS` with `contended: true` and `contendedFailure: { failure?, message }`, and every later limit is one lower (`readLimit()` less the alone passes, at least 1); failing alone, it is the alone run's `FAIL` and the limit stays. Either way it keeps the first attempt's `recorded` (`passed: false`), so `writeTestRun` and measured coverage leave the journey out of this run. `summariseResults` adds "(n after an alone rerun)" to the passed count, `compactTestResults` gives `contended: n`, `formatJourneyResult` prints the first failure under the `PASS` line, and `writeTestResults` keeps both fields in `results.json`. Headless runs and `--repeat` runs keep the limit at 1, so nothing runs beside anything and nothing reruns.
- **Browser slots stay shared** (decision `journeys-share-browser-slots`). Journeys take the same three browser slots as screenshots and every other browser operation, and `acquireMachineSlot` waiters poll rather than queue, so at 2 or more another session's screenshot can wait through several journeys, up to its five-minute limit. In the large-app measurement (LDF-1065) with two runs at 2 each, 7 of 13 screenshots waited over 60 s. The default stays 1 for this and for memory.
- **Timing.** The CLI's own time is the whole POST, which includes the slot wait. `runJourney` on the server adds `durationMs`, counted from the browser slot being taken, and `waitedMs` to every result it runs; the CLI's `runJourney.js` reports those when present and its POST time against an older server.
- **Traces.** A recorded full-suite run appends each actor's records to one `.jsonl` as they arrive, so overlapping journeys interleave. Every reader groups by session or by `run.journey`, never by position: `readNewestTestRun` filters on `run.by`, `compileSegments` groups by session through `normaliseRecords`, and `readMeasuredRun` picks passing journeys by `run.journey`. `compileSegments.test.js` checks an interleaved file compiles as each journey alone.

## Users, case tables and expanded runs

`validateJourneyUser` is the one rule for `user`: absent, an inline user object, `none`, a data set user name, or a non-empty list of distinct data set user names, which needs `data`. The dev server refuses the combinations that cannot work in `server-dev/lib/docs/dataSets/resolveJourneyDataSet.js` (the user docs list them). With no `user`, an active mock user acts; an explicit `user` wins over it (`getBrowser.js`, `openPage`).

A journey with a list runs once per user, and a journey with `cases` once per row. `expandJourney` makes one item per run, `{ filePath, journeyIndex, journey, expandedFrom }`, where `journey` is the run (`journeyRuns`) and `expandedFrom` the journey as written. A user run is `personaJourney`: the same journey with that one `user`, named `<name> [<user>]`. A row run (`expandCases`) is the journey without `cases`, each `{ _case: <key> }` filled in from the row anywhere in it, `user`, `data` and `pageId` included (`fillCase`), named `<name> [<row name>]`. A user list beside `cases`, a `_case` that fills `user` with a list, a `_case` naming a key its row lacks, an empty table and two rows with one name are refused. Everything downstream keys on the run's name: result lines, `--filter`, `--repeat`, the recording's `run.journey`, the `run.json` and `exercised.json` keys and harden baselines. Each run gets a fresh data session. A tier is cut once per journey, and all its runs go with it. `hashJourney` hashes the expanded run, so a changed row or shared file marks its `exercised.json` entry stale; `stubs` joins the hash only when a journey has them, so journeys without stubs keep their hashes.

Where a journey is read rather than run, it is read once (`collapseRuns`): a user list as the journey as written, and a case table as its first selected run, since as written it holds `_case` placeholders where lint, evidence and coverage read values. The first run stands for it (`measuredJourney`) in lint and evidence; `committedJourneys` expands discovered items first, so evidence and coverage read a case table the same way. L5 still checks every listed name. Variants are generated from the journey as written, with the first run's exercised path, and keep its user list or case table, so they replay once per user or row. On a case table, the generators that read who the journey runs as (`ROW_GENERATORS`: `empty`, `volume`, `roleGranted` and `tenant` on every row, `tenantCalls` on the first, whose run gave the payloads it replays) read each row's filled journey instead (`generateVariants`): a step passed through from the row is put back as written, the same variant from several rows is kept once, and each variant's `cases` holds the rows it came from, named in its detail when they are not all of them. `roleGranted`'s keep comment then says to add its rows with the key the `_case` user reads, or to make the user such a placeholder first. `lowdefy_run_tests` leaves a thrown run's `stack` out of the answer's entries; the first report holding it prints it once, and `results.json` keeps it on each.

`lowdefy_run_journey` takes a list and calls `runJourneyAsUsers`, returning `{ passed, runs: [{ user, ... }] }`. `POST /lowdefy-docs/journey` runs one user per call and refuses a list with a 400. Both take one inline journey, so neither takes `cases` or `_ref`; a file with them runs through `lowdefy test` or `lowdefy_run_tests`.

`as:` opens another actor (`createJourneyActors.js`, `switchTo` and `userFor`): `main` is the run's user, a data set user name opens as that user, and any other name opens as the journey's `user`. `checkActorName` in `checkStepReferences.js` checks the name before the step runs.

## Running a journey

`POST /lowdefy-docs/journey` (`server-dev/src/routes/docs/journey.js`) and `lowdefy_run_journey` (`server-dev/lib/docs/createDocsMcpServer.js`) call `runJourney` (`server-dev/lib/docs/runJourney.js`). In order, it:

1. checks the origin, `pageId`, `pathParams` and `urlQuery`,
2. runs `validateJourneySteps`, then `normaliseJourneySteps`, and refuses a step only the runner in process can take (`classifyJourney`'s `inProcess`: `hold`, `release`, a `call` as `system`), pointing to a headless run,
3. refuses a placeholder step (`findPlaceholderStep`),
4. checks the state selection, the timeout and mail use (`validateJourneyMail`),
5. builds the page URL (`buildPageUrl`) and resolves the data set (`resolveJourneyDataSet`),
6. inside a browser slot (`withBrowserSlot`): opens the data session and sets the journey's `stubs` on it (`addJourneyStubs`; the route and the MCP tool check them first with `validateJourneyStubs`), opens the browser and the recording identity, registers the run's error buffer, creates the app error watcher, opens the page, creates the step rails, runs the steps (`runJourneySteps.js`), reads the final state and collects the exercised path.

A refusal returns `{ error, refused: true }`, which the route answers with 400; other errors are 502; a mutant run on a stale build is 409. The result is `{ pageId, passed, steps: [{ index, step, status, durationMs }], screenshots, state | stateOmitted, exercised, failure?, data?, warnings?, sunk? }`, with `ready: false` and a `note` when the page never settled. `failure` is `{ index, step, expected, actual, message }` (`toFailure`); step indices are zero-based. `state` is left out over 10,000 characters (`stateOmitted`) or with `state: false`. A mutant run adds `mutant: { id, applied, misses }`. The MCP tool returns screenshots as image blocks and trims `exercised` to `{ counts, note }` unless asked for it (`selectExercised.js`).

**When a page counts as settled.** The page open, a `goto` and the settle after each interaction (`settlePage`, at most `SETTLE_TIMEOUT_MS`, 5 s) wait on `isPageReady`: init events done, no block event running, no request loading, subscriptions connected, no lazy block or held skeleton. An event is `loading` for its whole run, so a page that polls with a `Wait` (sleep a minute, read again, run again) always has one in flight. The engine's `createWait` marks such an event with `waitingUntil`, and each caller passes `isPageReady` its `deadline`, the time it gives up. An event whose wait ends after the deadline is not counted, since the caller could not outlast it and nothing changes because of it before then. A wait that ends within the window (a debounce before a request, a short pause in a click handler) still holds the page, exactly as before. The same holds for an `onInitAsync` (page or app) that sleeps past the deadline. The shell's `isContextSettled` applies the same rule.

Before each step, `checkStepReferences` fails a step whose block, request, endpoint, `goto` page or `as` name is not in the build. On a data set run a `click`, `open`, `fill` or `select` also passes the step rails first (see below).

### How a target resolves

`runJourneySteps.js` resolves targets with the selectors in `@lowdefy/helpers`' `journeyTargetSelectors`.

- `blockId`, `row` and `column` give the scope: the `#bl-<id>` wrapper, its `.ag-row[row-index]`, its `.ag-cell[col-id]`.
- `text` matches visible interactive controls whose text is exactly it. With no `blockId` it searches the front-most open layer that holds one: the last open `[role="menu"]`, then the last `[role="dialog"]`, then the page.
- A `blockId` target without `row` or `column` that uses `text` or `containing`, and `expect.text`, also search the block's Modal or Drawer portal, which carries the class `ldf-portal-<id>` (`journeyTargetSelectors.portalClass`, set in the antd `Modal` and `Drawer` blocks).
- `containing` matches visible elements whose text contains it. `nth` alone picks the nth interactive control in the scope. A target with none of these is the scope, clicked on its first control.
- Before choosing, a click or open waits for the control to be visible, for lazy blocks to load and for tables to clear a held loading skeleton (`waitForLoadingBlocks` on `window.__lowdefyLazyLoads` and `window.__lowdefySkeletonHolds`, the same counts `isPageReady` reads). A held skeleton gives way to the rows on a pointer press, so a click started on it would land on nothing.
- **Action targets must name one element.** For click, open, fill and select, `resolveActionTarget` waits for a first match, looks again and counts. More than one visible match without `nth` fails the step at once, naming the count and where it looked. Expectations accept any match.
- `rowKey` narrows the scope to the block's `.ag-row[row-id]` or `.lf-table-row[data-row-key]` (`gridSelector({ kind: 'rowKey' })`). A click with no `column` or `control` waits for the row, fails when several rows with a first cell carry the key, and clicks the row's `aria-colindex="1"` cell as a cell target (its first control, else the cell): AG Grid draws cells out of display order, so the first `.ag-cell` is not the first column. A generated key (`isGeneratedRowKey`, `__row_<n>`) fails the step before it acts, on clicks and on `expect.visible`, `hidden` and `text`, naming the block, its type and the fix.
- `control` (`locateControl`) is the one visible element marked with the block, key and row key (`controlSelector`), page-wide, or in the column's cell and the open `.ant-dropdown` popups when `column` is given (a cell menu draws its items in `document.body`). Elements inside an antd motion leave class (`ant-<motion>-leave`, as on a closing modal or popup) do not count; the runner lists the motions (`LEAVING_MOTIONS`) and matches whole class names, so a block id or class with `leave` in it is not taken as closing. While none shows, it hovers the keyed row once (Table's `showOn: hover` buttons mount only then), then opens the first closed `dropdownTrigger` in the scope (cell, else row, else block), else clicks the `data-popover` trigger whose hidden `data-popover-content` in the block holds a marked element (`findPopoverTrigger`, a `ClickableHtml` element in a popover): a block whose dropdown opens on hover (`DropdownMenu` with no `trigger`, or `trigger: hover`, read from the block's evaluated properties on the page) is hovered, a `trigger: contextMenu` block right-clicked, any other trigger clicked. A click's rails check (`checkStepRails`) runs before that first hover or open, since opening fires the block's `onOpenChange`. Several visible matches fail with the count. `expect.visible` and `expect.hidden` on a `control` target read the same visible marked elements (`controlMatches`; several visible fail `visible`). `open` opens a hover dropdown the same way, so the block in `DropdownMenu`'s `content` area is never clicked. A click on a hover dropdown's control rests on it for 300 ms first (`restOnHoverDropdownItem`): antd opens a hover dropdown `mouseEnterDelay` (0.15 s) after the pointer enters its popup, so a click inside that wait closes the dropdown and the timer opens it again, with `onOpenChange`, which no person's click does.

The recorder agrees: `describeElement` (engine `trace/createDescribeElement.js`) gives `nth` whenever the scope holds several matches, `0` included, and `null` only for a unique one. `resolveTargetInDocument` (`@lowdefy/e2e-utils/targets`) is the jsdom mirror the round-trip tests use; it resolves an ambiguous target to nothing, and handles `text` only (no `containing`, no portals). It also resolves `row_key` (the row by key; with no column, its `aria-colindex="1"` cell) and `control` (the one element marked with the block, key and row key, anywhere in the document, inside the column's cell when given, skipping elements the DOM itself hides), and refuses a generated row key. A marked control describes as a control target only when no other visible element (not hidden in the DOM either) carries its marks, since the runner refuses several matches: two keyless `ClickableHtml` elements with one event describe by their text.

## App errors fail a journey

A journey fails at the step that causes an app error its own browsers raised, even when every expectation holds.

- **Attribution.** Every run carries a verified recording identity: a recorded run the one its caller sends, any other run its own `{ source: 'journey', run: { id, by, journey: null }, record: false }` (`journeyRunRecording.js`). `clientErrorStore` and `serverErrorStore` hand any entry stamped by a journey run (`isRunErrorEntry`) to that run's buffer (`lib/docs/runErrorBuffers.js`: `registerRunBuffer`, `recordRunError`, `takeRunErrors`, `releaseRunBuffer`, keyed by run id and `run.journey`, kept on `globalThis`). Those entries never reach the shared error rings or the dev event bus, and an entry for a released buffer is dropped. So a journey's errors never reach build status, and a developer's own tab's errors never fail a journey.
- **Windows.** `createJourneyAppErrors` (`lib/docs/observe/`) hooks every actor context through `watchJourneyContext`: page errors, app API requests and responses, aborted requests and client error reports in flight. `runJourneySteps` judges contiguous windows: the page open (`judgeOpen`, a failure with `phase: 'open'` and every step skipped), each step (`judgeStep`, which waits for client error reports except after `expect`, `wait` and `screenshot`, though an `expect.error` step does wait), and a final drain after the last step when nothing has failed. `screenshotPage` runs without the watcher.
- **One classifier.** Each window goes through `evaluateInvariants`. Kinds `action-error`, `client-error`, `server-error`, `request-failed` and `dev-server` are errors; `dead-click` is a warning; `environment` is info. A finding with severity error, or of kind environment, fails the step; when any environment finding is present, the others are dropped, and the same goes for a `dev-server` finding, which comes from a response the proxy answered itself (`x-lowdefy-child`, see `startProxy.mjs`). Findings are deduplicated by `findingKey`. Expected outcomes are not findings: the error names in `@lowdefy/errors`' `expectedErrorNames` (`UserError`, `AuthenticationError`, `AuthorizationError`, `TwoFactorEnrolmentRequiredError`), a failed `Validate` and a `Throw`. On a `goto` step, fetch failures are dropped when the window saw an aborted request (`isCausedByGoto`), since navigating away aborts the old page's requests.
- **Failure shape** (`toAppErrorFailure`, `withAppErrors`): `{ index, step, kind: 'app-error', message, expected: 'no app error', actual: ['<kind>: <message>'], errors: [{ kind, message, source, configKey, key }] }`, with `source` relative to the config directory. A step that also failed on its own keeps its message as `stepMessage`. A `dev-server` finding makes it `kind: 'dev-server'`, `expected: 'the dev server to answer'`: the result says nothing about the app.
- **`expect.error`.** When the next step is `expect.error`, the interaction's findings are held. `claimExpectedErrors` claims held and its own window's findings whose message contains the text, plus any `action-error` once something matched (the trace carries no values, so an action error never holds the text). No match fails the expect step; anything unclaimed fails the interaction.
- **`expect.effect`.** Reads the previous window (`previousWindow`) and fails when `hasNoEffect`: no event, no DOM change, no app request, URL unchanged. The dead-click invariant uses the same check.
- **CLI.** `formatJourneyResult` prints an app error failure as `step N: <step>` or `on open`, and `formatAppErrors` prints one line per error with kind, message and `file:line`.

## Data sets

The file format and its rules are in `journey-data-sets.md`. `parseDataSet` (node-utils) is the one reader for the dev server, lint, variants, scope and coverage. It reads the files with `readDataSetFile` (which also refuses a `snapshot:` key), follows `extends` with `readDataSetFiles`, merges them with `mergeDataSetFiles`, then validates and expands `generate` (`validateDataSetGenerate`, `generateDataSetDocuments` in `dataSetGenerate/`). `adviseDataSetSize` gives the size advice.

The dev server reads a data set through `readDataSet`, which adds the checks that need the build, among them `checkSharedCollectionIds.js` for connections that share a collection. `openDataSession` opens a database on the dev server's own data store, and `loadDataSetCollection` loads indexes, then generated documents, then fixtures. A result's `data` is `{ name, loadMs, documents }`.

That code lives in `@lowdefy/test-utils/dataSets` (`packages/utils/test-utils/src/dataSets/`), so the endpoint test harness loads data and gates connections with the same implementation: the store (`getDataStore`), sessions (`openDataSession`, `dataSessionRegistry`, `sweepOrphanDatabases`), the reader and loaders, and the gate below (`applyDataSetRedirect`, `createDataSetRefusal`, `sinkExternalConnections`, `trackSessionWork`). The dev server still owns the store for journeys: it starts it in its own process and passes its own logger (`getDataStore({ logger })`, `openDataSession({ dataSet, logger })`). The harness has a store per test run instead (`getRunDataStore`, shared by the run's test processes and stopped with the runner) and passes it to `openDataSession({ dataSet, logger, store })`; on it a session's databases carry their process's pid and `sweepOrphanDatabases` drops by run. The dev server passes neither option. "The data store of a test run" in [testing.md](../testing.md#the-data-store-of-a-test-run) has the mechanism. What only the dev server needs stays in `server-dev/lib/docs/dataSets/`: `readDataSession` (the journey data cookie), `resolveJourneyDataSet` and `describeDataSetResult`.

The agent dev tools take `user` and `data` in the journey forms, without lists: `resolveToolCaller` and `withDataSession` (`lib/docs/`) give `lowdefy_screenshot_page`, `lowdefy_inspect_state`, `lowdefy_run_request` and `lowdefy_run_endpoint` a data session.

### Data-set modes

Under a data session every connection read goes through one gate, `applyDataSetRedirect` (`@lowdefy/test-utils/dataSets`), which reads the connection type's `meta.dataSet`:

- `redirect` merges the session database over the properties. A connection whose properties have a top-level operator key is refused.
- `walled` passes unchanged: the type holds no database URI and reaches MongoDB only through the walled client (`walled(connectionId)` from `packages/api/src/routes/request/createWalledResolver.js`, with `getWalledCollection` from `@lowdefy/connection-mongodb/walled`). The walled connections it names are read through the same gate and redirected.
- `external` keeps its target, and its requests are sunk (below).
- Anything else refuses. A read after the session closed throws.

The tenant wall's unwalled-reach verdict (`packages/api/src/routes/connections/resolveUnwalledReach.js`) reads the build directly, so it is the same in and out of sessions.

**Sinks.** `sinkExternalConnections` (`@lowdefy/test-utils/dataSets`), wired in `createLowdefyContext`, replaces every request resolver of an `external` connection type, and any single resolver that declares `external` on its own `meta`, with a sink. Each sunk request is recorded on the data session as `{ connectionId, connectionType, requestType, requestId, pageId, endpointId, request }`, with secrets scrubbed, and `runJourney` returns the list as `sunk`.

**Stubs and gates.** A journey's `stubs` are state on its data session, beside `sunk` (`addJourneyStubs`), and one function applies them on every host: `createSessionConnections` in test-utils, which test-utils' call context and `createLowdefyContext` both call (decision `session-hooks-on-the-data-session`; [utils/test-utils.md](../utils/test-utils.md#stubs-and-gates-on-the-data-session) has the mechanism). An answer stub answers a request type with its literal `answer`, narrowed by `requestId`, `endpoint`, `pageId` and `match` on the request as `sunk` records it; the first that matches answers and the request is still sunk. An answer stub on a connection or request type the app does not have is refused before the journey runs (`checkJourneyStubTargets`, the check `session.stub` runs): the build host when it opens, the dev server before the data set loads. A fail gate throws a `ServiceError` with the journey's message, branded forced (`markForcedFailure`), before the request runs, on any connection, once, `times: n` or `times: all`. Every host's error sink records the forced message by request id (`recordForcedFailure`; the dev server's only on a data session), `expect.error` after a `call`, `request` or `webhook` reads it there (`readForcedError`), and a forced error is never an app error: the wire carries `forced: true` (`createWireProjection`, from the brand alone), so a click's failed action is not one either. A webhook routine that failed answers 500 with no request id in its body, so the hosts' `webhook` answers the call's `rid`, and a browser run reads it from the `x-lowdefy-journey-request-id` header the dev server's endpoints route sends on a data session. A fail gate that never fired fails the journey at its last step (`findUnfiredFailGate`), unless something failed before; so does a journey's answer stub that names its request (`requestId`, `endpoint`, `pageId` or `match`) and never answered, after the gates (each counts `answered`, `listUnansweredStubs`, `describeAnswerStub`). A stub keyed only by its types is a fallback and may go unused. Both checks drain the session's background work (`session.work`, `drainSessionWork`) first, so a request only `context.waitUntil` work makes is counted. `expect: { sunk }` (`expectSunk`) checks what was sunk, stubbed requests included, narrowed by `connectionType`, `requestType` and `requestId`, with `count` and `match` on the last one.

**Origin guard.** The data cookie is scoped to the journey's origin, so a request to the dev server's port under another host (127.0.0.1 against localhost, `[::1]`, a LAN address) would carry none and read the real database. `getBrowser({ origin })` keeps one browser per origin host and port (`lifecycleForOrigin.js`, keyed by `originGuard.js`), launched with Chromium's `--host-resolver-rules` from `hostResolverRules.js` (`MAP *:<port> ~NOTFOUND, EXCLUDE <host>`): every other host on that port fails to resolve, so such a request never leaves the browser. `openPage` refuses a data cookie in a browser launched for another origin. `watchJourneyOrigin.js` listens for those requests and the runner fails the step that made one (`Journey left its origin ...`). It is a request listener, not a Playwright route, because any route turns the context's HTTP cache off: each page load then refetched every dependency chunk (on the fixture app about 1,540 requests and 67 MB a load; with the cache a later load transfers 0.2 MB). Every headless caller on that origin (screenshots, inspection) shares the guarded browser. An origin on a default port (80 or 443, a proxy or tunnel) refuses every other site on that port, as the route before it did, and now for those callers too. The rules only apply to a host Chromium resolves itself; a proxy resolves the host of a request it carries, and would reach the dev server under a LAN address, `mymac.local` or an `/etc/hosts` alias. So `proxyLaunchArgs.js` makes the proxy configuration explicit at launch: a proxy the environment names (`HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, with `NO_PROXY`) becomes `--proxy-server` with `--proxy-bypass-list=*:<port>`, so every host on the dev server's port goes direct and meets the rules, and with no such variable the browser gets `--no-proxy-server`. A proxy set only in the operating system (macOS network settings, a debugging proxy such as Charles or Proxyman) is not used by the headless browsers, because Chromium takes a bypass list only with an explicit proxy server. `journeyOriginGuard.chromium.test.mjs` proves both paths with a proxy of its own.

### Step rails

The rails cover the steps that act on a block and can fire its events, listed with the words their refusals use in node-utils' `journeyRails/railedSteps.js`: `click`, `open` (a dropdown's `onOpenChange`), `fill` and `select` (an input's `onChange`), and `press` (the focused block's events, and any event a block binds to the chord with `shortcut`). `back` and the other steps are not railed. A headless press is Enter in the input the runner filled last, checked against the blocks the browser's `checkPressRails` checks (`checkHeadlessPressRails`): that input, each block around it up to an enclosing Modal, Drawer or ConfirmModal (where the browser's DOM walk ends at the portal), and each shown block whose `shortcut` Enter fires (`pressFiresShortcut`, which moved to journey-headless so both runners share it). Each step that acts on one element makes one rails check (`createStepRails` in `runJourneySteps.js`) before it first acts on the page: `open` on the dropdown trigger before `openDropdown`, `fill` on the input or colour picker trigger, and `select` on the element it picks in, before it picks: the native `<select>`, the radio or checkbox option labelled with the value (the option itself, since a container can hold a second group), or the element it clicks to open the dropdown.

A `press` is checked by `checkPressRails` before the key goes down, against every block the chord can fire events on. Around the focused element: each block whose `#bl-` wrapper holds it (an input's `onPressEnter` or `onChange`, a button's `onClick` on Enter, a container's `onClick` it bubbles to), the block a control mark around it names (a modal's OK button in its portal) and the block whose portal class (`portalClass`, matched against the engine's block ids) is on an ancestor (Escape fires a Modal's `onCancel` and `onClose`, a Drawer's `onClose`). Then each block the page's engine holds whose own `visible` is not false and that binds an event to the chord. `pressFiresShortcut` decides that with tinykeys itself (`parseKeybinding`, `matchKeybindingPress`) on the shortcut as the client binds it (`normalizeShortcut` from `@lowdefy/client/createShortcutManager.js`), against the key and code Playwright's US layout sends, with `$mod` as the page's modifier; a sequence is matched by its last chord. A shortcut without a modifier is checked even while focus is in an input, where tinykeys skips it, and a sequence's last chord is refused without the chords before it: both refuse too much. The auth rail runs after a press settles, as for the other steps; its message names the innermost block around the focused element, or the one block a shortcut fires, when that is the only block the press acts on.

On a data set run, `runJourney` sets `journey.dataSetRails` from node-utils' `createDataSetRails({ readArtifact, connections })` (`journeyRails/`), reading the build through `readBuildArtifact` and the connection plugin map from `readConnectionPlugins`. Each page's lists are read from the build once per run. The headless runner checks the same rails (see Headless runs).

- **Before a step acts**, `checkStepRails` reads the block it acts on: the target's `blockId` for a `control` or `rowKey` target (a modal footer or popup control sits outside every block wrapper; checked before the runner hovers a row or opens a dropdown to show the control), else the nearest `#bl-` wrapper of the element the target resolved to, so `text` and `containing` targets are covered, or the target's `blockId` for an element outside every wrapper (a `fill` into the Search modal's portal input). A click also checks the `DropdownMenu` whose content holds that block, since the click reaches the dropdown's trigger and opens it (`onOpenChange`); headless checks the same two blocks (`runHeadlessStep`'s `railClick`: the block the click lands on, a plain click on a `DropdownMenu` landing on its first content control, then `findContentTrigger`). Then `findExternalBlocks` lists, per block, the connections it reaches through a `Request` or a `CallAPI` into endpoint routines that a data set cannot run. An `external` type with request resolvers is left off the list, since its requests are sunk (`isSunk`). Which declarations are refused, and the messages, are in `journey-data-sets.md`.
- **While the step runs**, `armAuthActionRecorder` (`checkAuthActionsRan.js`) installs `installAuthActionRecorder` in the page, which wraps each auth engine method listed in `authEngineMethods.js` and notes calls in session storage. After the step settles, `checkAuthActionsRan` reads the record (`readAuthActionRecorder`) and fails the step only if an auth action ran.

## Journey cookies

One helper writes and reads every cookie the dev server's headless browser sets on a journey context: `server-dev/lib/server/journeyCookies.js` re-exports `writeJourneyCookie`, `readJourneyCookie`, `forwardJourneyCookies` and `JOURNEY_COOKIES` from `lib/server/journeyCookies/`. Each value is `<token>.<payload>`, the token minted once per process (`lib/server/auth/journeyActor.js`). `readJourneyCookie` compares the prefix with `timingSafeEqual`, so a cookie from anywhere else is ignored. The production server reads none of them.

| Cookie      | Name                     | Kind     | Forwarded on loopback |
| ----------- | ------------------------ | -------- | --------------------- |
| `actor`     | `lowdefy_journey_actor`  | inline   | no                    |
| `recording` | `lowdefy_recording`      | inline   | no                    |
| `data`      | `lowdefy_journey_data`   | registry | yes                   |
| `mutant`    | `lowdefy_journey_mutant` | registry | yes                   |

An inline cookie carries its meaning (an actor's client address, a recording label); a registry cookie carries the id of an in-memory entry for one run. `createLowdefyContext` is the one writer of `context.loopbackHeaders` (`{ cookie }` of the verified forwarded cookies, `{}` when none), which a detached `CallApi` carries, so a detached hop still reads the data set and the mutant. `forwardJourneyCookies` also forwards a data cookie for a data session a dev tool call opened itself.

## The exercised path

Every journey result carries `exercised`: `pages`, `appEvents`, `requests` (with call counts), `endpoints` (nested `CallApi` targets as `via` with `calls: null`), `unfollowed` (computed endpoint ids), a `write` flag on each request and endpoint (from the request type's `meta.checkWrite`, transitive through nested endpoints), `events`, `rendered` and `controls` (`collectExercised.js`, `addNestedEndpoints.js`, `addWriteFlags.js`). `controls` lists, for each browser click by `text`, `containing`, `nth` or `row`, the control marks of the element it landed on when one visible element carries them (`readMarkedControl` in `runJourneySteps.js`): `{ stepIndex, blockId, control, rowKey }`. Lint L8 suggests it as the step's target.

- Network: one `context.on('request')` counter per actor (`createNetworkCounter`), which survives full page loads. `expect.calls` reads it.
- Page side: `createJourneyActors` exposes a `__lowdefyJourneyObserve` binding on each actor context. `client/JourneyObserver.jsx`, rendered beside `Inspector`, starts `client/journeyObserver/startJourneyObserver.js` only where that binding exists. It subscribes to the engine trace hook without state and samples visible blocks (`lib/client/collectVisibleBlockIds.js`: a shown `bl-` wrapper with size, or a Modal or Drawer while one of its `ar-<id>-<slot>` wrappers is shown) in the frame after any DOM change. The runner samples again at each settle. List indices normalise to `$`.
- `lowdefy test` keeps each journey's newest path in `.lowdefy/test/exercised.json`: `{ version: 1, buildId, journeys: { "<file>#<name>": { hash, passed, exercised } } }` (`writeExercised.js`). An entry is ignored once the journey's hash changes.

## Traces and session logs

A **trace** is JSONL of v1 records (`node-utils/src/journeyTrace/`: `validateTraceRecord`, `validateTraceEvent`, `validateTraceTarget`, `TRACE_VERSION`). Sources are `production`, `dev` and `journey`; only a `journey` record carries `run`. A record is one DOM interaction (`pageview`, `click`, `change`, `key`, `back`, `pageleave`) joined to the engine event it caused, or one `engine` record no interaction caused (scope `page` or `app`).

- `event` has three states: an object, `null` (watched, none ran) or absent (production cannot see successes; only production may leave it out, and production may not use `null`).
- A dev event lists the action types it ran (`actions`), the requests and endpoints it called (`requests`, `endpoints`, each `{ id, ok, ms }`), its state writes, invalid blocks, URL after, and error. The engine stamps the calling action's id on each `CallAPI` response, as on request calls.
- Production records carry no values and no query values (`hasQueryValues`). They carry `path_params` on page views, `frustration` (rage or dead click), and hashed person and organization ids.
- `pairTraceEvents` (`@lowdefy/helpers`) is the one rule for which interaction caused which event: an ancestor block, the latest interaction within `debounceMs + 1000` ms; mount and app events never pair; within a pair the innermost block's event comes first. The web and phone dev recorders (`@lowdefy/client-core` `recorder/createPairingBuffer.js`) and the production pull (`journeys/pull/pairFailures.js`) all call it.
- Layout: dev and journey traces are `.lowdefy/traces/<source>/<yyyy-mm-dd>/<id>.jsonl` (`lib/server/recording/appendRecords.js`); production is `.lowdefy/traces/production/<day>.jsonl` with `<day>.manifest.json` and the `salt` file. `isRecordingEnabled` reads `LOWDEFY_DEV_RECORD`; `manager/utils/startRecordingPruner.mjs` runs `pruneRecordings.mjs` over dev and journey traces at start and then hourly.

**Session logs.** The coding agent writes journeys from session logs and proves each with `lowdefy test --repeat 3`; no command writes journey files. `formatSessionLog` (`node-utils/src/sessionLog/`) validates one session's records, folds them as the compiler does (`normaliseRecords`, `segmentSession`, `foldInteractions`) and renders each through `describeLogRecord` as one line: the step's verb, target and value, then `→` what the app did. It throws unless the records hold exactly one session, and returns `{ id, start, end, lines }`. `summariseSessions`, `buildSessionReport` and `formatSessionReport` serve `lowdefy journeys session` (`cli/src/commands/journeys/session/`); with `--source dev`, `--from` and `--to` are refused. The `lowdefy_journey_session` dev tool reads the app's own dev traces (`server-dev/lib/docs/readJourneySession.js`).

**Segments.** `compileSegments` (`node-utils/src/journeyCompiler/`, pure; sources `production` and `journey`) groups records by session, filters source and window, cuts each tab into segments (`segmentSession`: 5 minutes idle, or an uncaused page view), folds DOM noise, compiles each segment to steps (`compileSegment`) and hashes its `journeySequence` (sha1, 8 hex). A segment with no interaction step is dropped. Each segment also carries its failure path, frustrations, text clicks and person, organization and role sets. Evidence refresh, coverage and the measured test run (`readMeasuredRun.js`) read it.

**Identity.** `stepIdentity` is the verb (`open` reads as `click`), the list-normalised block id, column, click text and press chord, as a JSON array. `journeySequence` is `[{ page, identity }]` per interaction step. It moves pages at `goto`, and at an `expect.url` path only through the route table (`loadRouteTable`: the build's routes and base path); steps after an `email` step are skipped until the next page move. Both take an optional `isConfigText`: with it, a click's text enters the identity only when it is config text.

## Production text

The PostHog plugin's `before_send` masks clicked text the page config does not spell out, unless `PostHogInit` sets `maskDataText: false` (see [posthog.md](../plugins/plugins/posthog.md)). On the CLI side, clicked text is never stored either. `lowdefy journeys pull posthog` (`cli/src/commands/journeys/pull/`, the HogQL query API) writes `target.text_token` and no `target.text`. `tokenText` gives `t_` and 16 hex of HMAC-SHA256 under the trace salt over `text:` and the text normalised by `normaliseClickText`. The text is `lowdefy_text`, falling back to `$el_text`. A click on a marked control reads `lowdefy_control` into `target.control` with no `text_token`, as the dev recorder records it. An event without `lowdefy_block_id` falls back to the masked chain, read with `targetFromElementsChain(chain, { rowKey: false })` after its `data-lf-control` marks are dropped: the enrichment sends a block id for every mark it accepts, so a mark there is one it declined (a cell control in a row with a generated key, whose key the masked chain no longer holds), and it reads by text, as dev does; PostHog never holds a row key, so a cell control keeps its displayed `row`, which `stepIdentity` leaves out as it leaves out `rowKey`. A click on a cell control whose row key several rows of the grid share is recorded in dev by its row and text (`findMarkedControl` in `createDescribeElement.js` checks the other rows). The enrichment sees only the clicked chain, not the other rows, so PostHog's production pull records the same click as `{ control }` and the two identities differ. The gap is accepted: a row key is the row's own id, so a shared one is a data fault the dev recording already shows. Person and organization ids are `p_` and `o_` HMACs (`hashId`). Each day manifest has `text_rule: 'token'`, the salt's `salt_id` (first 8 hex of its SHA-256, `readTraceSalt`) and the pull's filters (`project_id`, `environment`, `filter_test_accounts`). A target needs a `block_id`, a `text` or a `text_token`.

**The config text set** is every string the built config can show: page string leaves (operator arguments included), `menus.json`, every locale's i18n messages and labels, every plugin's default messages, and antd's locale strings (`en_US` for a locale with no antd name, and without i18n). The installed dev server's builder (`server-dev/lib/configTree/buildConfigTree.mjs`, collected by `collectConfigText.mjs`) writes it as `configText.json`, spawned through `cli/src/commands/journeys/configBuilder/` and shared with `journeys scope`. `readConfigText` caches it under `.lowdefy/journeys/config-text/<hash>/`, keyed on the config files (not `tests/`, `.lowdefy/`, `node_modules/`, `.git`), the `--ref-resolver` option and the builder version. A cached read costs a hash of the config files; a stale one costs a full config build.

**Resolving tokens.** `createTokenResolver`, applied per record by `resolveRecordText`, turns a token back into text only when it is the token of a known string, and always deletes `target.text`. Session logs and coverage resolve against the config text set. Evidence refresh also resolves against the click texts the committed journeys' live and deprecated flows already hold (`evidence/committedFlowTexts.js`), so a renamed label's old clicks still back the old flow. `countTextTokens` gives, per page, block and column, the clicks, distinct unresolved tokens and the top 5 tokens with persons; `profileProduction` adds them to `coverage.json` as `production.textTokens`.

**Readers.** `readProductionTrace` (async, a window with no gaps) serves production session logs and coverage through `readProductionSegments.js`: a missing day is an error naming the pull to run, and a window that mixes days pulled with different filters is refused (`checkPullFilters`). `readProductionMonths` reads whole months, gaps allowed, plus the final day just outside each month, for evidence refresh. A day hashed under another salt is read by neither: the strict reader names it missing, and `listFinalDays` leaves it out. Pull, session logs and coverage refuse a window over 30 UTC days (`parseTraceWindow` with `MINING_WINDOW_MAX_DAYS`).

**Upgrade.** `removeUntokenisedTraces` runs at the start of a pull and before every production read, evidence refresh included. When a day manifest lacks `text_rule: 'token'` it deletes those days, `tests/journeys/_candidates/production/` and `.lowdefy/test/coverage.json`. It also deletes what a stopped pull left (`.tmp` files, a day file with no manifest) once it is 10 minutes old.

## Coverage

`lowdefy journeys coverage --source production` (`journeysCoverage.js`, `coverageReport/`) writes `.lowdefy/test/coverage.json`, version 2 (`coverageReportVersion.js`; a report of another version reads as none). It holds `generated`, `source`, `window`, `flowGrouping`, five measures (interaction, flow, failure, frustration, role) with ranked uncovered lists, the production profile, each journey's sequence and an optional `mutation` score.

- Two pure functions in `node-utils/src/journeyEvidence/` carry it. `isBackedBy`: a segment backs a journey when the journey's sequence is an in-order subsequence of the segment's, from the segment's first entry on the journey's page; an empty journey sequence is never backed. `profileProduction`: ranked flows per entry page, failure paths, frustrated blocks, role sets per page, entry pages and text tokens.
- Sessions are grouped into flows only from `FLOW_GROUPING_MIN_ROWS` (100,000) rows in the window, or with `--group`; `--no-group` never groups (`decideFlowGrouping` returns `{ grouped, rows, threshold, forced }`). Ungrouped, `measures.flow` is null and `production.flows` is empty.
- `deprecated: true` journeys are left out of every measure. The role measure reads data set user names as role sets (`readJourneyDataSetUsers.js`).
- Other commands read the report instead of profiling production again: `journeys scope` uses `production.entryPoints` for app-wide changes, variants use `production.roleMatrix`, and `journeys usage` lists uncovered flows from it (`readUncoveredFlows.js`).

## Production evidence

`lowdefy journeys evidence --refresh` (`journeysEvidence.js`, `evidence/`) is the only writer of a journey's `evidence` key, and splices only that node into the file (`writeEvidenceNode`, one flow-style line per month). Without `--refresh` it prints the changes. A journey's `evidence` holds `production`, `mutation` (copied from `.lowdefy/test/mutation.json` by `readMutationReport`) and `refreshed`; `journeySchema.js` refuses any other key, and a `dev` key with a message to delete it.

`evidence.production` is `{ sequence, pageId, flow, months, deprecated? }`, each month `{ month, days, sessions, persons, orgs, failures }`.

- `days` is how many final days of the month the refresh read. `listFinalDays` returns the days whose manifest says `final: true` (the pull re-pulls today and yesterday) and whose `salt_id` is this machine's, as `{ days, otherSalt }`, and refuses a cache pulled with mixed filters.
- `sessions` counts backing segments that started in the month (`bucketByMonth` on `first_seen`); `failures` those with a failed event; `persons` and `orgs` are distinct within the month. A month read with no backing segment is written with `sessions: 0`; a month never read is absent.
- `selectMonthsToRead` picks a month where some counted flow has no entry or fewer days than the cache, every cached month for a live flow rehashed under a new matcher, and the current month (and the previous one across a month boundary). `readProductionMonths` reads them, and `compileSegments` compiles them.
- `mergeMonths` writes the cache's numbers for a month only when the cache holds more final days than the committed entry, or as many on a recount. So refreshing twice changes nothing, a fuller cache on another machine wins, and a pruned or never-pulled month keeps its committed values. With no readable final day, production evidence is kept as committed.
- The older window shape (`sessions`, `share`, `window`) still validates (`legacyProductionSchema`), and the next refresh replaces it with months.
- `formatZeroBacked` lists the journeys nothing backs over the last 3 months, beside their mutation numbers. No command removes a journey for low traffic.

**The sequence id** is `v<SEQUENCE_VERSION>-` and `hashSequence({ pageId, sequence })` (`evidence/sequenceId.js`, which exports `SEQUENCE_VERSION`, 1; `sequenceVersion.js` reads the version back out of a stored id), over `journeySequence` with `isConfigText` and the route table. `flowLines` gives the `<page> <identity>` lines it hashes, stored as `flow`; `parseFlowLines` turns them back into a sequence for `isBackedBy`, so a flow is still counted after its steps are gone.

**Deprecated flows.** `reconcileFlows` compares a journey's current id with its stored one. The same id moves nothing. Another id at the same version moves the committed months to a new `deprecated` entry `{ sequence, pageId, flow, replaced, months }` and starts the live flow empty, unless the current id equals one of the journey's deprecated entries, which becomes live again with its months. An older version (a matcher change) is rehashed without deprecating, and its months are recounted. Deprecated flows are counted on every refresh; one stored under an older version stays uncounted (`isCountedFlow`). No command deletes a deprecated entry.

## Tiers and usage

`computeTiers` (`cli/src/commands/journeys/usage/`) is the one ranking that `journeys usage` and `selectTier` read.

- **Rate.** A journey's `sessions` over the `days` of its months inside the usage window: the last N calendar months (`parseUsageWindow`, default `3m`) ending at the newest month any selected journey's live flow holds (`newestMonth`), so a run ranks over one calendar (`windowUsage`).
- **Cut.** Ranked journeys sort by rate, then file, then name. Tier pX is the shortest prefix whose summed rate reaches X% of the total (`tiers.js`: `common` 50, `wide` 80, `edge` 95, `full` 0), with journeys tied at the cut included. Every match counts, so a tier's share is a share of journey matches, not of sessions.
- **Thin data.** Fewer than 100 matches in the window (`MIN_MATCHES`), or no ranked journey with days, refuses every tier but `full`.
- **Unranked journeys** have no counts for their current flow: never refreshed, the older shape, or edited since the last refresh. `isUnranked` first compares the id read with every click text against the stored one, and only then the id read with `isConfigText`. `readTierConfigText` reads the config text set only when some live journey's id differs from its stored one, and `selectTier` skips it for tier `full`, so a full run never pays for a config build. An unranked journey is in every tier, outside the ranking and the total (`inTier.js`).

`selectTier` keeps the selected items in the tier and returns deprecated journeys as skipped. The PASS line comes from `formatEvidence`, a skipped journey's line from `formatSkippedJourney`. A tiered run is not a full-suite run, so it records nothing. The advice to run `tier: common` first and `edge` before calling a change done is one text, `TESTING_RULES` in `agentSetup/testingRules.js`, written into AGENTS.md and the `lowdefy-config` skill.

`journeys usage` (`journeysUsage.js`) selects as `lowdefy test` does, then `committedJourneys`. `buildUsageRows` adds to each `computeTiers` row `allTime { sessions, failures }`, its months and its deprecated flows with their window use. `--json` prints `{ windowMonths, anchor, matches, rows, uncovered }`, where `uncovered` is `{ window, flowGrouping, flows }` from the coverage report, or `null` when there is no report of the current version. With `--tier` and a refusal it exits 1.

## Headless runs

A headless run takes the journeys that need no browser and runs them in Node: the page's own event chains on `@lowdefy/engine` and `@lowdefy/client-core`, its requests and endpoint calls in process through `@lowdefy/api`, no React and no DOM. The design is "Headless journeys" in Pelican, under the cheaper journey testing project.

**Classification.** `classifyJourney({ journey })` (node-utils `journeyGrammar/`) reads the steps alone: `{ headless: true }`, or `{ headless: false, index, step, reason }` for the first step that needs a browser (`screenshot`, `email`, `press` other than Enter or Escape, a `fill` from an email, a click with `count` above 1, a `text`, `containing`, `row` or `nth` target or a `column` without `rowKey`, `expect` `text`, `title` or `effect`). `open` and the `rowKey` and `control` target keys are headless: both runners read a row and a control by key (`journeyTargetSelectors.gridSelector({ kind: 'rowKey' })`, `controlSelector`, the `data-lf-block`/`data-lf-control`/`data-lf-row-key` marks, `isGeneratedRowKey`). The reasons for `row` and `text` name `rowKey` and `control` as the headless replacements. A step can still need the browser at run time; the runner reports that (below). Lint L8 runs it on the journey with its page-reading targets swapped (for a click, the control its measured run clicked, from `exercised.controls`; else the `blockId` alone), to name journeys one key away from headless.

**The host.** The runner never imports from a server. It takes a host (`createHeadlessHost.js` documents and checks the shape): `rootConfig`, `readPageConfig({ pageId | path, pathParams, urlQuery, user })`, `loadClientPlugins()`, `call({ kind, pageId, requestId, endpointId, blockId, actionId, payload, user })` answering as test-utils' `answerCall`, `findDocuments` for `expect.db`, `readArtifact(name)` for step reference checks and the data-set rails, `connections` (the app's connection plugin map, as the data-session gate reads it), `resolveUser`, `userNames`, `dataSetName`, `dataSession`, `errorSink` and `close`. `createBuildHost({ app, data, stubs, user })` builds it on a production build through `@lowdefy/test-utils` (`openSession` and the `./headless` export `headlessCalls(session)`), so the build checks, secret removal and data sessions are test-utils' own. A `lowdefy test --headless --build` run opens the build once (`openBuildApp` in `test.js`, test-utils' `openTestApp`), and the build check, the access step and every journey run use that app; each journey run gets a host whose `close()` ends only its own session. `test.js` opens that app with the `LOWDEFY_TEST_SECRET_*` values of the command's environment as `secrets` (`readTestSecrets.js`), so a journey can compare a secret with data while every other secret keeps its stand-in; `LOWDEFY_SECRET_*`, from the shell, CI or `.env`, is never read for a test run. test-utils' `scrubSecrets` redacts every secret value of 8 or more characters in sunk records, so `expect.sunk` and a stub `match` cannot match a secret that is also a data-set id. A page that does not exist or the caller may not open shows the `404` page, as the page route redirects. The second host is the dev server's, `createDevServerHost` in server-dev `lib/docs/`: pages are built on demand and read, and requests and endpoints run in the dev server's own process through `@lowdefy/api` (`createInProcessRequest.js`), as its routes run them, on the journey's data session, with its recording and mutant cookies, so a harden mutant applies. `POST /lowdefy-docs/journey` with `headless: true` runs `runJourneyHeadless.js` on it, with no browser slot; `lowdefy test --headless` (no `--build`) posts there, takes no journey run slot and writes `headless-run.json` with mode `dev`, and `lowdefy_run_tests` and `lowdefy_run_journey` take `headless`.

**A page in Node.** `loadClientPlugins` imports the build's `plugins/actions.js`, `plugins/operators/client.js` and `plugins/operators/clientJsMap.js` and reads `plugins/blockMetas.json`; no block component loads. Every action in `browserOnlyActions.js` (the auth family, browser APIs, `PdfMake`) is a stub that fails with "<Action> needs the browser." An actor (`createHeadlessActor.js`, one per person, as the browser runner's actors) builds `lowdefy` with `createLowdefyCore` on a Node host (`createNodeClientHost.js`: `window.location` from the page path, a 1440 by 900 viewport, no `document`, memory stores) and replaces what the web client adds: `callRequest` and `callAPI` go to `host.call` and are recorded with payload, response and error (`createPageCalls.js`); `handleError` and the logger feed the error sink; `link` follows a page link as a client-side navigation on the same `lowdefy`; `displayMessage` is recorded; the websocket client is inert (`createInertWebSocketClient.js`): a subscribe resolves on the next tick, as the server's ack comes a round trip later, and calls `onConnected`, so the channel reads connected and its `onSubscribe` fires after the blocks' `onMount` has started; no message ever arrives (a step that fails while the page holds a subscription open names it, `noteSilentSubscriptions.js`), no `auth.websockets` rule is checked, and a `Publish` marks the journey browser-only, since it needs the server's channel. Showing a page runs the app's and page's `onInit` and `onInitAsync`, then opens the page's subscriptions (`subscribeAll`, as the web client's `WebSocketsEffect` does; the next page shown closes them, unless it is the same context, which the web client keeps mounted), then every block's `onMount` in React's mount order (`collectMountOrder.js`: children before the block, a hidden block's subtree, a loading block's content when it shows its object `skeleton`, and a closed Modal's content left out), and reports block parse errors as the web client's `Block` does. Loading is worked out as `Block.js` does: the block's own `onMount` still running (`page.mountFinished`), its parent's loading passed down (except into a `Table`'s slots, which keep their own, `SLOTS_KEEP_OWN_LOADING.js`), or its own `loading`. The actor registers an updater for every block in the engine's `updaters`, as each `Block` component does, and checks the mounts again a microtask after the engine updates a block or a block's `onMount` finishes (`checkMounts` in `createHeadlessActor.js`, `fireMountEvents.js`): content a skeleton held back mounts once loading ends, a block that hides or shows its skeleton unmounts its content (`standIns/unmountContent.js`) and starts its own component's state again (`standIns/unmountComponent.js`: an open Modal or Drawer shows closed), and a hidden block that shows mounts its children. `page.mounted` maps each mounted Block instance to a token for that mount, so an `onMount` that finishes after its block unmounted leaves the new mount loading. Each check registers the methods of the blocks that now render first (`registerBlockStandIns`), as components register them before React runs `onMount`.

**What React's components do.** `registerBlockStandIns.js` registers the methods `CallMethod` calls: `setOpen` and `toggleOpen` on `Modal` and `Drawer` (by block type, since both are category `container`) keep an open state that `onOpen`, `onClose` and mounting the content follow, and a `list` block's item methods are its engine methods. On a block whose type has a stand-in, a method the stand-in does not register fails `CallMethod` naming the block and method. A block whose type has none (one from the app's own plugin, or a Lowdefy block such as `Title`) first registers the methods its meta declares in `headlessMethods` (`{ [method]: event or null }`, carried into `plugins/blockMetas.json`; `standIns/registerHeadlessMethods.js`), once the browser would render it (`collectRenderedBlocks`: mounted, not hidden and not showing its skeleton), as its component registers them as it renders: each fires that block event with the method's first argument as the event and returns its result, so `CallMethod` waits for its actions, as the component's `methods.triggerEvent` does. A method declared `null` changes only what the block draws, so it registers a no-op: `CallMethod` resolves with `undefined` at once. Any other value fails, naming the block type and method (block-utils' `checkHeadlessMethods`, which the build runs too as it writes `blockMetas.json`). The parity journey is `apps/journey-fixture/tests/journeys/_parity/plugin_block.yaml`. Then its `methods` are wrapped (`standIns/leaveMethodsToBrowser.js`): its component registers its other methods in the browser, so any method it has not registered marks the journey browser-only at that point, naming the block, its type and the method. The engine's `CallMethod` is the only reader of `block.methods`. `visible` and `hidden` read whether the block's component renders (`collectRenderedBlocks`, so content behind a skeleton is hidden), `visibleEval` of the block and every ancestor and the open state of each Modal or Drawer around it (`isBlockShown.js`), not pixels: the real difference from the browser for portals and CSS.

**Stand-ins by block type.** `BLOCK_STAND_INS.js` maps a block type to what its component does for a step: a `rowKey` or `control` click, `open`, a plain click a dropdown answers, `expect.visible`/`hidden` on a `rowKey`. A step on a type with no part for it marks the journey browser-only, naming the block and its type. `ClickableHtml` (`standIns/clickableHtmlStandIn.js`) reads its rendered `html` in jsdom (`loadHtmlDom`, sanitised as `HtmlComponent` does) and lists the `data-event` elements its `dataEvents` lists, keyed by event and `data-id` (`listHtmlControls`, which uses block-utils' own `findDataEventRule` and `getDataEvent`): elements the html hides are left out, and an element in `data-popover` content counts for a click when a trigger opens it, as the browser runner opens it. A click fires the event with the browser's event object; an event whose `dataEvents` entry or `data-confirm` asks first keeps a confirm open (`state.confirm`, `state.open`) whose `ok` fires it and `cancel`, another click or `leave` drops it. `expect.visible` and `expect.hidden` count the shown elements, or the open confirm's buttons. The grids leave an expectation on a cell `control` to the browser. The grids (`AgGridAlpine`, `AgGridBalham`, `AgGridMaterial`, `AgGridLowdefy`, `Table`) share `standIns/createGridStandIn.js`: a row by its key (each grid's rule; a generated `__row_` key, no match and several matches fail), its first cell in display order (pinned start, unpinned, pinned end), `onCellClick` then `onRowClick` in the grid's shape, and a cell's buttons, menu items and AgGrid switch firing their own events. `Table` reads columns, row keys, `{ when }` conditions, formula values and the column rules that load enrichment or editing (`columnNeedsEnrichment`, `columnNeedsEditing`) through `@lowdefy/blocks-antd/table/`, as blocks-table does; AgGrid's few rules are copied, `columnGroupShow` applied at every level of nesting as AG Grid 36 does. A grid feature that changes the rows a person sees (a sort, filter, pagination, selection, views; for `Table`, any property `standIns/TABLE_PROPERTIES.js` does not class modelled or looks-only, or a column key `standIns/TABLE_COLUMN_KEYS.js` classes browser-only, each checked against Table's meta by a test) leaves the step to the browser, as does every row step on an AgGrid after a `CallMethod` with `setFilterModel` or `setQuickFilter`. A `CallMethod` with any other grid method leaves the journey to the browser at that step, naming the method (`registerBrowserOnlyMethods`): every Table method (`standIns/TABLE_METHODS.js`, checked against Table's meta by a test; `setFilter` and `setSearch` write the table's value and fire `onChange`, `applyTransaction` returns the rows it changed), and AgGrid's `autoSize`, `exportDataAsCsv` and `sizeColumnsToFit`. So does a click on a cell the stand-in does not draw: a link or input cell, an AgGrid custom `cellRenderer`, and a `Table` `html` cell whose html for that row holds `a[href]`, `a[data-page-id]` (the link enhancer gives it an href) or `[data-event]`. `readHtmlCell` works out the html as `HtmlCell` does, with the Table's template compiler, and `htmlHoldsCellControl` sanitises it with DOMPurify on a jsdom window loaded on first use, as `HtmlComponent` does in the browser; plain formatted html stays headless.

**Popups and dropdowns.** A `Modal` or `Drawer` with `destroyOnHidden` (and no `forceRender`) unmounts its content when it closes, as `ConfirmModal` does (`standIns/unmountContent.js`): the next open mounts it again and fires `onMount`, and what its blocks' components keep (a dropdown's open state, a nested popup's) starts again, while engine state stays. A `DropdownMenu`'s `content` area is its trigger, so a plain click on a block in it is a pointer click (`pointerClick.js`): the block's `onClick`, then the trigger, which toggles a click dropdown and opens a hover one. When a block on the way has `onClick` actions without `bubble: true`, the engine skips the dropdown's events for that DOM click (`claimDomEvent`), which `isClickClaimed.js` copies: a click dropdown opens or closes and fires no `onOpenChange`. A Modal, Drawer or ConfirmModal in the content draws in a portal, so a click inside it reaches no trigger. A plain click on a `DropdownMenu` lands on the first input or `onClick` block in its content, children first (`standIns/findContentControl.js`), as the browser runner clicks the first control inside a block; an input there leaves the step to the browser. A `ColorSelector` fill clicks the picker first (`fillColorSelector.js`); the Escape that closes the picker reaches no dropdown. `open` on a dropdown already open fails, as the browser's shows no new popup.

**Escape.** `pressEscape.js` takes `press: Escape` wherever the focus is. In the browser, antd keeps every open Modal, Drawer and trigger popup (dropdowns, select dropdowns, popovers) on one portal stack (`@rc-component/portal`'s `useEscKeyDown`) and closes the newest; rc-dropdown also closes every open dropdown on its own window listener (`useAccessibility`), and ClickableHtml's `HtmlOverlay` closes its newest popover or confirm. The stand-ins keep popups in the order they opened (`page.openBlocks`) and dropdowns only as open or closed, with no order between the two, so the runner closes the one open dropdown, search or confirm when no popup is open or it sits in the newest popup's content (it opened after the popup, which showed it), and otherwise the newest popup. Each type's `escape` part does what its component does: a Modal fires `onCancel` and closes unless it failed or bounced (antd's `handleCancel`; nothing with `keyboard: false`), a Drawer runs its close (nothing with `keyboard: false`), a DropdownButton or DropdownMenu fires `onOpenChange { open: false }`, a Selector, TreeSelector or TreeMultipleSelector clears its search as the focus leaving it does, a MultipleSelector closes and keeps its search (rc-select does), and a ClickableHtml confirm drops its event (its `isOpen` part reads whether new html closed it). `runHeadlessStep`'s `noteFocus` keeps `page.inputFocused` and `page.pointerBlockId`: a fill or select leaves the focus in its input (`lastInputBlockId()`), a click or an open that clicks moves it off (an open that hovers a dropdown, as `openDropdown` in `runJourneySteps.js` does, leaves it), a click or open moves the pointer to its block, and an Escape that closes a popup hands the focus back off any input. Escape goes to the browser at run time, naming why, when nothing is open, two dropdowns are, a dropdown is open beside the newest popup, a shown block binds Escape as an event shortcut (`findShortcutBlocks.js`, which `checkHeadlessPressRails` shares) or, with no input focused, as an item shortcut (blocks-antd's `useItemShortcuts` on Tabs, Menu, DropdownMenu and DropdownButton), the pointer rests on a block that can show a tooltip or popover there and no popup mask covers it (a trigger popup opened after the overlay takes the Escape), a Modal or Drawer has `forceRender` (its portal is on the stack while closed), the newest overlay is a ConfirmModal, or the focus is in an input that handles Escape itself: a TextInput or NumberInput with `onEscape`, or any type outside `ESCAPE_PASSING_INPUT_TYPES.js`. On a data-set journey the rails check the block with the focus and the blocks around it up to the popup (the focused input, else the block the pointer rests on when it is in the overlay or is the overlay, except a ClickableHtml confirm, whose focus is in its own popup), then the overlay Escape closes. The browser runner waits, up to a second, for every antd motion (`-appear`, `-enter`, `-leave` of the `LEAVING_MOTIONS`) to end before it presses Escape (`waitForOverlayMotion` in `runJourneySteps.js`): an overlay mid-motion keeps its place on the stack, so an Escape straight after a close reaches the closing overlay again (a second `onCancel`) and one straight after an open beats its `afterOpenChange`. The parity journeys are `apps/journey-fixture/tests/journeys/_parity/escape.yaml`, on `escape_targets`.

**Steps.** Block steps go through client-core's `createStepRunner` (`src/steps/`, shared with the phone shell): an event is started without waiting on it and the step waits on the capped settle, so a long debounce never holds a step, and `select` on a list-valued block ticks the option. A `fill` fires `onChange` with `{ value }`, as text, number and colour inputs' views do (PhoneNumberInput's fill is refused; a browser fill finds no text input in a Calendar or ListSelector, which `checkFillTarget` still lets through, and their extra `date`, `index` and `item` are not modelled), so a chain reading `_event: value` runs headless. A `select` matches an option by the text its label shows: the host passes `readLabelText({ block, label })`, and journey-headless gives `readOptionLabelText.js`, which reads the html text (`readHtmlText.js`, in jsdom, as Playwright's text match does) for the types in `HTML_LABEL_TYPES.js` and the label as written for any other. The phone shell gives none, since a native picker draws the label as plain text. The runner's `readOptionTexts` is the one lookup, which the searching selectors' stand-in uses too. Before a select, `findTextWritingLabel.js` lists it browser-only when a label uses `data-avatar`, `data-format` or `data-time`, whose browser text the html does not hold; after closing other dropdowns, a select on a dropdown waits a task (`waitForNextTask.js`), so a single selector's deferred `onSearch ''` starts before the pick's `onChange`, as the browser's open click lets it; a select on an inline option (`INLINE_OPTION_TYPES.js`) is one click, so its `onChange` starts first. Before that the runner waits for the target to be shown, refuses a `fill` the browser would refuse (`checkFillTarget.js`), marks a click on a block with no `onClick` browser-only (a browser lands it on a control inside), and waits for `wait: { request }` calls made since the last interaction (`waitForRequestCall.js`). On a journey with a data set (`host.dataSetName` set), `runHeadlessJourney` makes the run's `createDataSetRails` from `host.readArtifact` and `host.connections`, and `checkHeadlessRails.js` refuses a `click`, `open`, `fill`, `select` or `press` before it acts with the browser's message, expected and actual: on the clicked block, on a `rowKey` or `control` target's own block before its stand-in opens a dropdown, and on the input the step runner presses Enter in (`lastInputBlockId()`), which the fill before it has already checked. A `select` through a container fails headless as "not an input" before any rail applies, since the step runner selects by `blockId` only. The auth-action rail stays the browser's: the auth actions are browser-only headless. `goto` is a full load; `back` replays the actor's history. `checkStepReferences.js` checks blocks, requests, endpoints, `goto` pages and `as` names against the build, as the browser runner's does. `call` and `request` post the payload as given through `host.call`, as the step's `as` without switching actor, and their answer is what `expect.status` and `expect.error` read; `expect.db` reads `host.findDocuments`, test-utils' `findSessionDocuments`, which revives the fixture markers in `match` (`deserializeFixture`) and answers with documents as a request would (`toDocumentJson`: a Decimal128 as `{ '~dec' }`, not the driver's `{ $numberDecimal }`); `expect.calls` with `payload` or `response` matches the last call partially.

**Races, system calls and webhooks.** `hold` sets a pause gate on the data session; `createJourneyRaces.js` races each later `call` or `request` against the open gates (`raceToPauseGate`), so a call that reaches one is parked and its step passes. `release` lets the parked call go, waits for it, and makes its answer the one later expect steps read. It matches the parked call with `matchesRequestKey` on the request that reached the gate (`gate.reachedBy`, set by `holdAtPauseGate`), so `release: { requestId, endpoint, pageId }` picks between two holds on one request id; `release: <requestId>` lets the first parked at that id go. An `expect` straight after a parked call, and a call still parked at the end, name the release step to write; when another bare hold shares the request id it is the object form with the endpoint (or page) the call reached the gate in. When that release would also let go another parked call, the hint (`hold` on the parked answer, `quoteParkedRelease.js`) names the step of the call's hold, and either suggests `release: { requestId, endpoint, pageId }` when the whole request names only this call, or names the calls parked before it that the release lets go first. A gate no call reached, or a call still parked at the end, fails the journey (`listUnreachedPauseGates`); the gates are released either way. A click whose request reaches a gate fails its step. `expect.calls` counts only the current actor's calls. A `call` `as: system` goes to `host.system` (`runDetachedEndpoint` with a system principal), and a `webhook` step to `host.webhook` (`runWebhookEndpoint` with its raw body, so the endpoint's `verify` gate runs); `system` is reserved as a data set user name. `classifyJourney` marks `hold`, `release` and `as: system` `inProcess`, which a browser run refuses.

**App errors.** `createAppErrorWindows.js` judges each step's window with the invariants in node-utils `journeyInvariants/`, which server-dev's `evaluateInvariants` also uses for its browser-independent part: the trace emits (the engine's trace registry, as the browser's step observer reads it), the client errors the sink took (expected outcomes and errors the server already logged left out), and the server faults of the calls made in the window, a search-stage fault being an environment finding. A fault a `:catch` of the routine handled never reaches the sink (`addServerFaults.js` leaves out a fault marked `caught`, which `controlTry` tells each host's fault sink once its `:catch` has run, `settleCaughtFaults.js`): the routine answered, so the journey judges the answer. That is how a routine that catches an auth step passes on the build host, which has no auth engine. A detached `CallApi` needs no `:catch`: both headless hosts set `context.sendDetached` (`handleEndpointCall`'s seam; a server without one sends over `/api/detached` through `sendDetachedRequest`). The build host records the call and never runs its target (test-utils `createDetachedRecorder`); the dev server host sends it as always and records it once sent. Either way the answer's `detached` lists it, and `recordDetachedCalls` puts it on the calling actor's calls (the current actor's for a `webhook` step), so `expect.calls` reads it as a call to its target with its payload. A browser run does not see it. A browser run judges a caught fault the same way: the dev server's `createHandleError` stamps the store entry `caught`, and `findErrorEntries` leaves it out, so a caught config, operator or internal error fails neither runner. A fault the `:catch` passes on (`:throw: { _error: true }`) or fails on is not caught, and fails both. A caught fault is still logged in the terminal and sent to error tracking; one a journey run caused stays in that run's error buffer, so it is in neither build status nor the journey's result. `isExplained` in `evaluateInvariants` lets no caught entry explain a 5xx. The open is judged on its errors only. `expect.error` claims as in the browser runner, after an interaction or a call (`held.answered`).

**Result.** `runHeadlessJourney` answers as `runJourney` does (`pageId`, `passed`, `steps`, `state`, `failure`), plus `calls` and `messages`, or `browserOnly: { index, step, reason }` with no `passed`, for a journey classified or found at run time to need a browser. A browser-only mark during the page's open (an `onMount` `CallMethod` on a block with no stand-in) answers `browserOnly: { phase: 'open', reason }`, and wins over any failure the open raised, as a step's mark wins over its failure, since the browser run judges the journey; a browser-only action (`SetFocus`, `Logout`) during the open does the same. The CLI line says `on open`. On the dev server host a headless run reports what it exercised (pages, requests and endpoints with their write flags, completed events, through `onTrace`), so `exercised.json` counts it; neither host writes trace recordings, so session logs do not include headless runs.

**Parity.** server-dev's journey fixture client (`test/journeyFixture/fixtureClient.mjs`, `checkParity.mjs`) reruns every journey a fixture test posts that `classifyJourney` calls headless on a production build of the fixture, and fails the test when passed, the failing step, the app error count or the asked state selection differ. The records land in `apps/journey-fixture/.lowdefy/parity/`. The CLI's `headlessParity.test.mjs` does the same for the journey files through `lowdefy test` and `lowdefy test --headless --build`.

## Hardening

**Replay.** `lowdefy test --repeat <n>` (1 to 10, `parseRepeat.js`) runs each journey n times (`runRepeated.js`) and `classifyRuns` marks it PASS, FLAKY or FAIL, with `phase: 'open'` for a failure at open. A refused journey fails once.

**Lint.** `lowdefy test --lint` (`cli/src/commands/test/lint/`, one file per rule, L1 to L8) reads data sets from their files and needs no server. L2, L4 and L8 read the newest measured run from `exercised.json`. A journey with a user list or a case table is linted once (`collapseRuns`).

**Config mutants.** `POST /lowdefy-docs/mutants` (`server-dev/src/routes/docs/mutants.js`) builds the pages first (a page that fails to build is a 422 with its errors; a page no longer in the app lists nothing), reads the build id, and lists mutants (`drop-action`, `skip-validate`, `flip-visible`, `swap-if`, `drop-payload`, `retarget-link`, `drop-block`, `drop-step`) on the artifacts a set of runs exercised. Each is addressed by `~k` within one build, with a build-independent `id`, an `anchor`, `source` and `config`. `groupMutantCopies` (`lib/server/mutants/`) folds the copies a `_ref` puts on several pages into one mutant kept on the first page, listing the rest as `copies` and `copyTargets: [{ artifact, key, anchor, pointer }]`. A journey POST with `mutant` (which may carry `pointer` and `nodeHash`, to find the node again after a page rebuild) opens a run in `mutantRuns` (a registry on `globalThis`), writes the mutant cookie on every actor, and `createMutantReadConfigFile` serves that run's requests a mutated copy of one artifact, counting `applied` and `misses`. A stale build id is a 409.

**`lowdefy journeys harden`** (`cli/src/commands/journeys/harden/`, options in `parseHardenOptions.js`):

1. `selectJourneys` leaves out journeys without `data:` with an error, and exits 1 when none is left. `--page` narrows the baseline through `exercised.json` (`narrowBaseline.js`).
2. Baseline each journey, each persona run of a journey with a user list.
3. List mutants on the union of the baselines' paths, keep those on a journey's path (`isOnPath`), and run each against the copy that journey reached (`findOnPathCopy`). Sample by sha1 of seed and id.
4. Run (mutant, journey) pairs on workers: a journey never beside itself, mail journeys alone. Verdicts are killed, survived, unapplied and error; an error runs once more. Progress lines come from `createProgress.js`, the `--list` estimate from `estimateRun.js`.
5. Carry verdicts over config edits (`carryOverVerdicts`); the third change stops the run.
6. Score and write `.lowdefy/test/mutation.json` (`buildMutationReport`): `{ version, generated, buildId, rebuilds, killed, total, sampled: { max, of, seed }, operators, mutants, journeys: [{ file, name, killed, total, unique }] }`. Each mutant is `{ id, operator, artifact, source, config, describe, copies, status, ranBy: [{ file, name, verdict, failure, misses }] }`, status one of killed, survived, unapplied, errored, changed or not run (`mutantStatus.js`). The report merges per journey (`writeMutationReport.js`, `mergeMutationReport.js`): an earlier mutant is kept only while the dev server still lists it (`requestCurrentMutantIds.js`). A `--mutant` run writes nothing.

**`lowdefy journeys variants`** (`cli/src/commands/journeys/variants/`, one generator per kind in `generators/`) writes candidates under `tests/journeys/_candidates/variants/<source>/`, each with `variant: { of, kind, detail }` and a header line holding a hash of what was generated, and replays each three times. A granted role variant skips the role sets the journey's listed users already hold.

## Pull request scope

`lowdefy journeys scope [--base <ref>] [--json]` (`cli/src/commands/journeys/scope/`, driven by `journeysScope.js`) needs no running dev server, only the installed one under `.lowdefy/dev`, which it installs first (`ensureDevServer.js`, the installer `lowdefy dev` uses, starting no server) until an install has finished (`node_modules/.lowdefy-install-hash`; a `lowdefy: local` server is left alone), and otherwise writes only its caches:

1. `pruneScopeDirectory` drops cache entries unused for 14 days.
2. `resolveRevisions`: the merge base with `--base`, the working tree as head (with a `dirty` flag).
3. `materialiseTree` writes the base commit into `.lowdefy/scope/trees/<sha>/`.
4. `buildConfigTrees` builds both with the head's builder (`server-dev/lib/configTree/buildConfigTree.mjs`), cached under `.lowdefy/scope/builds/<sha>-<builderVersion>/`; a dirty head builds into a per-run folder removed afterwards.
5. `readBuildArtifacts`, `diffBuilds` and `selectTargets` (which fills each page's `blocks` with `diffPageBlocks`). Reasons are `page`, `request:`, `endpoint:`, `connection:`, `websocket:`, `app-wide`, `base-not-built`, and `head` when there is no `--base` (`selectHeadPages`, every page but `404`). A `_ref` change shows on every page whose artifact holds it. App-wide changes target the top 3 production entry pages from `coverage.json`, else the home page (`readCoverage`).
6. `readPluginSets`, `readDataSetUsers` and `describePageRoles` (`{ access: public | signed-in | roles, roles, users: [{ dataSet, user, roles }] }`), then `createScope`.

## Agent skills

`lowdefy agent-setup` writes the journey skills from `agentSetup/skills/` (`index.js` lists them): `journeys-from-dev`, `journeys-from-production`, `journeys-from-pr` (also the bug bash, given a goal sentence), `journeys-harden` and `journeys-autopilot`. Each keeps only journeys that pass `lowdefy test --repeat 3`. The skills read session logs, scope and config and write the journeys themselves. Each carries the section `skills/testLevel.js` renders, "Where each check lives": a page's logic and writes are a journey that needs no browser (`blockId` targets, `expect.state`, `expect.calls`, `expect: { db }`), what a page would never send and endpoint and server logic are a page-less journey (`call`, `request`, `webhook`, `cases`, `stubs`, `hold` and `release`, `as: system`), only what a journey cannot say is a test-utils test whose file says why, and who can reach what is `tests/access.yaml`, which `lowdefy test` checks on the production build (see [Test levels](../testing.md#test-levels)). The `role` variant kind writes only granted variants: which role reaches which page is the access table's to check, so no refused variant is generated.
