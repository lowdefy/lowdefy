# blocks-table architecture

`Table` is an input block whose value is its UI state, `{ view, selected, expanded }` (design D2, D6). This note is for whoever adds the next feature module. Design: `lowdefy-design/designs/table/design.md`. Benchmarks: `bench/RESULTS.md`.

## Layers

```
blocks/Table/Table.js         createLazyBlock wrapper: meta, size-stable fallback, method proxies
blocks/Table/Table.lazy.js    the implementation chunk (TanStack Table + Virtual + everything below)
core/TableRoot.js             config, data, table state, TanStack instance, block-level feature hooks
core/Grid.js                  the window component: layout, scroll-driven state, grid-level hooks, DOM
core/Body.js, Row.js, Cell.js rows of the current range, memoised by row key and row object
features/<name>/              feature modules, composed through features/index.js
```

Scrolling renders `Grid` and never `TableRoot`, so the engine and the block's own props are untouched by scroll (D10.2).

## State and value

- One React state object (`useTableState`) holds every slice: TanStack's (`sorting`, `columnSizing`, `columnOrder`, `columnPinning`, `columnVisibility`, `rowSelection`), feature-owned non-TanStack slices (`selectionMode`, `grouping`, `collapsedGroups`, `aggregates`, `expanded` from the expansion module), and the core's (`density`, `viewPassthrough`). TanStack is controlled with it (`state` plus generated `on<Slice>Change` handlers), so TanStack APIs such as `column.toggleSorting` and `row.toggleSelected` go through the same path.
- A change goes through `api.updateSlice(name, updater, { cause })`. It records a pending cause; after the change commits, the value is derived (`deriveValue`) and written once with `methods.setValue`, then `onChange { value, cause }` and each feature's `onCommit` fire. Drags and scroll never call it until the gesture ends.
- A slice with `transition: true` (sorting) updates inside `startTransition`: the click paints at once and the table is dimmed (`data-pending`) until the new order lands.
- A value changed from outside (SetState, Reset) re-initialises the state. SetState on a path mutates the object the table wrote, so the comparison is JSON for `view` and identity for `selected` / `expanded` (`getValueSignature`). A null value (mount, Reset) is filled with the resolved default value, without `onChange`.
- Resolution rules (`createInitialState`, `resolveViewColumns`, `pickViewPart`): each top-level view part falls back value → `defaultView` → column defaults. Unknown view column keys are dropped. Declared columns missing from a stored `view.columns` are appended hidden; `defaultView.columns` entries merge over the column defaults and unlisted columns keep their defaults. A derived view leaves `columns` out while it still equals the configured layout, so columns added to config (or loaded from a request) keep showing up until the user changes the layout.

## Data path

One pipeline in `TableRoot`, each stage a set of feature hooks run in registry order (`features/index.js`):

| Stage           | Hook / code                         | Input → output                                                    | Modules (in order)                                                                                            |
| --------------- | ----------------------------------- | ----------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 1. source       | `useData(ctx)` (`useFeatureData`)   | `properties.data` (or `[]`) → source rows                         | serverData (the block cache's loaded rows), tree (flattens `childrenField` rows)                              |
| 2. key diff     | `stabilizeData`                     | source rows → rows whose identity only changes with their content | core                                                                                                          |
| 3. row overlays | `useRows(ctx)` (`useFeatureRows`)   | stable rows → the rows TanStack sees                              | transactions (`applyTransaction` overlay), editing (Table's optimistic overlay, TableInput's changeset)       |
| 4. row model    | TanStack                            | rows → `table.getRowModel().rows` (filtered, sorted)              | sorting, filtering (manual in server mode), selection                                                         |
| 5. display list | `useItems(ctx)` (`useFeatureItems`) | row model rows → display items, `dataRows`, `rowOffsets`          | serverData (rows, server groups, holes), grouping (client groups), tree (tree rows), expandable (detail rows) |
| 6. window       | Grid, virtualization                | display items → the rendered range                                | virtualization, serverRange (loads the blocks behind the range)                                               |

- Stage 1 hooks see raw rows: `properties.data` is often a new array of new objects after every engine update. Stage 3 hooks see rows diffed by key (positional fast path, `rowVersionField` or structural compare), so they can hold state on row identity: an overlay entry applies until its row is a different object. Transactions come before editing so an optimistic edit shows over pushed changes, and a pushed change to an edited row settles the edit.
- TanStack uses `createStableCoreRowModel` (reuses `Row` instances; one changed row patches one row) and `createIndexSortedRowModel` (typed `Float64Array` keys per column, index sort, keys cached per rows array; big text columns build their keys in time slices before the sort applies).
- Rows re-render only when their row object, display index, selection, active column or the visible column list changes.
- Every hook returns its input (the same array, or null from `useItems`) when it has nothing to change, which keeps the memos downstream warm.

### The display list

What the window renders (`api.rows`, Grid's `rows`) is one flat list. Without a `useItems` hook changing it, it is TanStack's row model rows. Entries:

- a TanStack `Row` (a data row),
- a wrapped data row `{ kind: 'row', id, original, row, index, depth?, hasChildren?, expanded?, parentId?, expandable?, detailExpanded? }` (tree rows, expandable rows); Row renders the features' `cellLead` components in its first data cell and sets `aria-level` / `aria-expanded`,
- a group header `{ kind: 'group', key, depth, columnKey, value, empty, count, aggregates, collapsed, ... }`. Client groups (`flattenGroups`) add their leaf range `start`, `end`; server groups (`buildServerItems`) add `groupPath` (the values naming the group's own list) and start collapsed. `key` is the JSON of the group's value path. Both render with grouping's `GroupRow` and the sticky `StickyGroupRow`, and toggle through grouping's `toggleGroup` (server mode: `api.serverStore.toggleGroup`),
- a detail row `{ kind: 'detail', key, parentId, original }` (expandable),
- `undefined`: a server row that is not loaded yet, rendered as a `SkeletonRow`.

`core/isDataItem.js` tells data rows from the rest; code that walks `api.rows` for data rows uses it. `api.dataRows` is the view's data rows in display order: a hook's `dataRows` (grouping: the leaves, including rows of collapsed groups; export reads it), else the list's data items. `Body` renders a non-row item with its feature's `rowRenderers[kind]`, with the same props as `Row` plus `item` and `layout`.

Item heights: an item is one row high unless a `useItems` hook returns `rowHeights(item, index)` for it (expandable detail rows measure themselves). With any height function, the core builds `rowOffsets` (item tops, length n + 1) with `computeRowOffsets`, and the window, the body height, `scrollToCell` and the sticky group header use them instead of `index * rowHeight`.

## Server mode (D9)

`features/serverData`. `data: { mode: server, request, blockSize, maxBlocks }` registers the internal event `__tableFetch` (a Request action for `data.request`) and fetches with `{ startRow, endRow, view: { sort, filter, search, group, aggregates }, groupPath, selected }`; `view.aggregates` is the aggregates in effect (the view's over the columns' `aggregate` defaults). `createServerStore` owns:

- a `createBlockCache` per view: blocks of `blockSize` rows per list (the root list `[]` and each expanded group's list, keyed by `JSON.stringify(groupPath)`), LRU-evicted beyond `maxBlocks` loaded blocks, never evicting a visible or loading block. `invalidate()` bumps a generation: responses that started before are ignored (triggerEvent cannot be aborted) and invalidated blocks stay on screen until they reload.
- the view: `useServerView` derives it with `deriveValue`, so it follows whichever module owns sort, filter, search or group. A new view gets a new cache, scrolls to the top, fetches block 0, and keeps the previous cache on screen (`pending`, dimmed) until the new root block lands; responses for a superseded view's cache are ignored.
- loading: `serverRange` (grid level, after virtualisation) hands every rendered range to `onRange`. Slow range changes load the missing blocks at once; fast ones (above 0.05 rows/ms, about 2000px/s) wait until the range settles for 120ms. A block landing re-renders with the same range and never cuts a pending settle short.
- the display list (`buildServerItems`): the root list's rows, or its groups with expanded groups followed by their own list, with `undefined` holes for unloaded rows. `segments` map item runs to list rows, which is how a range maps to blocks (`getNeededBlocks`). `total` from the responses sizes the lists, the scroll height and `aria-rowcount`. Group rows carry the response's `count` and `aggregates`; the root list's `aggregates` are `api.serverStore.getAggregates()` (for the summary footer). Client grouping adds no rows in server mode; it only provides `api.grouping` (levels, aggregate functions, the group indices of the server list) for the group rows.
- open server groups live in the store (`toggleGroup`, `collapseAllGroups`), not in the value, and reset when `view.group` changes. Server groups have no group checkbox (their rows are not in the browser).

TanStack sees only the loaded leaf rows (`manualSorting`/`manualFiltering`/`manualGrouping`), for selection, row lookup and events. Selection is always preserved in server mode; the header checkbox writes `{ all: true, except: [] }` (`selectionMode: 'all'`), and `api.selectionExcept` remembers exceptions whose rows were evicted. `exportCsv` fires `onExport { view }`. `refresh()` invalidates the cache; `applyTransaction` merges updates into loaded rows and refetches the visible rows for adds and removes. Row moves are blocked in server mode.

## Trees and expandable rows

`features/expansion` owns the `expanded` slice (row keys, the value's `expanded`) and `toggleRowExpanded` (fires `onRowExpand`); tree rows and expandable rows both read it. `features/tree` (client mode only) flattens `childrenField` rows in `useData`, builds the parent/children index from the core rows (`parentField` links rows to the row with that key; missing parents and cycles make roots) and the display list from the row model rows in `useItems`: siblings keep the row model order (so a sort sorts within levels) and ancestors the filter left out are kept, placed before their first descendant. `api.tree` gives `rowSelection.cascade` and Right/Left their descendants and parents. A tree is never grouped (grouping stays inactive and offers no header menu entry) and its rows cannot be moved. The scroller's role is `treegrid`. `features/expandable` wraps rows with their expand state and adds a `detail` item after expanded rows; `DetailRow` renders `expandable.template` (nunjucks, compiled once in `useTableConfig`) through `renderHtml` and measures itself.

## Layout contract

`computeLayout` returns the visual column order (`start` = leading columns + start-pinned, `center`, `end`) with widths, sticky offsets, centre prefix offsets, and CSS variables on the root: `--lf-w<n>` (width of layout column `n`), `--lf-l<n>` / `--lf-r<n>` (sticky offsets), `--lf-total`, `--lf-center-w`; the scroller carries `--lf-center-before` (the column-virtualisation spacer). Cells use the column's shared `style` object. `api.previewLayout({ widths })` recomputes and writes the variables without rendering: use it for any drag.

## Feature module

A module is a plain object exported from `features/<name>/<name>Feature.js` and listed in `features/index.js`. Order matters: it is the order of handlers and hooks. Every field is optional.

| Field                               | Shape                                                                                           | Used for                                                                                                                                                                                                                       |
| ----------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `name`                              | string                                                                                          | keys, debugging                                                                                                                                                                                                                |
| `tableFeatures`                     | object of TanStack slots                                                                        | merged once into the stable feature set (`core/tableFeatures.js`), e.g. `{ columnFilteringFeature, filteredRowModel: createFilteredRowModel() }`                                                                               |
| `slices`                            | `{ [slice]: { init(args), cause, transition?, normalize?({ next, api }) } }`                    | state the module owns; `init` receives `{ value, defaultView, config, viewColumns, rows, getKey }` and resolves the slice from the value                                                                                       |
| `viewKeys`                          | string[]                                                                                        | view keys the module owns; the rest of the view passes through unchanged                                                                                                                                                       |
| `toValue({ state, api })`           | `{ view?: {...}, [valueKey]: ... }`                                                             | the module's part of the block value                                                                                                                                                                                           |
| `toViewColumn({ key, state, api })` | partial `{ width, pinned, hidden }`                                                             | decorates each `view.columns` entry                                                                                                                                                                                            |
| `tableOptions({ config })`          | object                                                                                          | TanStack options derived from config (memoised on config)                                                                                                                                                                      |
| `actions`                           | `{ name: (api) => fn }`                                                                         | functions other modules call through `api.actions` (`toggleSort`, `toggleRowSelected`, `activateRow`, ...)                                                                                                                     |
| `methods`                           | `{ name: (api) => fn }`                                                                         | block methods, registered with `methods.registerMethod`; also declare them in `meta.methods` (the lazy wrapper proxies declared methods)                                                                                       |
| `gridHandlers`                      | `{ click \| dblclick \| auxclick \| pointerdown \| keydown \| focus: (event, api) => boolean }` | the one delegated listener per event type on the root (D5); return `true` to stop the chain                                                                                                                                    |
| `headerParts`                       | components `({ api, col, state })`                                                              | rendered in every data header cell after the title                                                                                                                                                                             |
| `headerCellProps({ col, state })`   | attribute object                                                                                | extra attributes on data header cells (e.g. `aria-sort`)                                                                                                                                                                       |
| `onCommit({ cause, value, api })`   | function                                                                                        | runs after a value write (e.g. `onSelectionChange`)                                                                                                                                                                            |
| `useData(ctx)`                      | hook → rows                                                                                     | data pipeline stage 1, before the key diff; `ctx = { api, config, data, properties }`; returns the source rows (server rows, tree flattening)                                                                                  |
| `useRows(ctx)`                      | hook → rows                                                                                     | stage 3, after the key diff, before TanStack; `ctx = { api, config, input, properties, rows }`; returns the rows TanStack sees (transaction overlay, then editing's overlay / changeset)                                       |
| `useItems(ctx)`                     | hook → `{ rows, dataRows?, rowHeights? }` or null                                               | stage 5, after the row model; `ctx = { api, config, rowHeight, rows, state, table }`; replaces the display list (server items, client groups, tree rows, detail rows; see The display list)                                    |
| `useFeature(ctx)`                   | hook → fragment                                                                                 | block-level; `ctx = { api, config, data, state, table }`; fragment keys: `leadingColumns`, `regions: { top, bottom }`, `loading` (skeleton / progress), `pending` (dim the rows)                                               |
| `rowRenderers`                      | `{ [kind]: Component }`                                                                         | row components for display-list items of that kind (grouping: `group`, expandable: `detail`); props as `Row` plus `item` and `layout`                                                                                          |
| `cellLead`                          | component `({ api, item })`                                                                     | rendered before the content of a wrapped row item's first data cell (tree indent and chevron, expand chevron)                                                                                                                  |
| `bodyOverlay`                       | component                                                                                       | rendered once between the header and the body rows when there are rows (the sticky group header); props `{ api, centerCols, headerHeight, layout, rowClassName, rows, selectable, selection, sticky }`                         |
| `headerMenuItems({ column, api })`  | `[{ key, label, icon?, danger?, disabled?, onClick() }]`                                        | entries the headerMenu feature adds to the column's menu, collected in registry order                                                                                                                                          |
| `useGridFeature(ctx)`               | hook → object merged into the grid context                                                      | grid-level (re-runs on scroll); `ctx = { api, config, headerHeight, layout, rowHeight, rows, scrollerRef, state, strategy, viewport }` plus earlier modules' results (`range` from virtualisation, `activeCell` from keyboard) |

`api` (`core/createApi.js`) is one stable object per table, refreshed every render: `table`, `config`, `state`, `layout`, `rows`, `dataRows`, `rowHeight`, `rowOffsets`, `headerHeight`, `rootRef`, `scrollerRef`, `methods`, `components`, `updateSlice`, `setSliceSilently`, `previewLayout`, `actions`, `keyboard`, `suppressClick()` / `takeSuppressedClick()` (a drag that ends on a header must not also sort).

DOM contract for handlers: body rows carry `data-row-key` (TanStack row id = `String(rowKey)`) and `data-row-index` (display index; the header row is `-1`); cells carry `data-lf-cell`, `data-col-key`, `data-col-index` (layout index); header cells `data-lf-header`; special columns `data-special`.

## Adding the planned modules

- **headerMenu**: `headerParts` (menu button, lazy antd `Dropdown` mounted on open), `actions.openHeaderMenu`, a `gridHandlers.click` placed before sorting's (return `true` for the button), and `pin`/`hide`/`sort` through `api.updateSlice('columnPinning' | 'columnVisibility' | 'sorting', ...)`.
- **filtering**: `tableFeatures: { columnFilteringFeature, globalFilteringFeature, filteredRowModel }` where the row model compiles `view.filter` once with `core/compileCondition.js`; slices for the condition and search; `viewKeys: ['filter', 'search']`; `toValue` writes them back; a `headerCellProps` flag for the active-filter icon.
- **toolbar**: `useFeature` returning `regions.top`; `viewKeys: ['density', ...]` only if it takes density over from the core (then move `density` out of `claimedViewKeys`).
- **views** (`persist`, saved views): a `useFeature` effect that reads/writes `api.state` through `deriveValue` / `updateSlice`, and events `onViewSave`/`onViewSelect`; `api.updateSlice` for each slice when a view loads.
- **grouping** (built, `features/grouping/`): not TanStack's grouping, whose grouped model runs before sorting. `useGrouping` (a `useItems` hook) takes the sorted row model (after filtering, before pagination), builds the group tree in one pass (`buildGroupTree`: counts, leaf ranges and per-group aggregates with the shared `computeAggregate`), and flattens it (`flattenGroups`) into the display list; collapsing reruns only the flatten. Slices `grouping` (column keys, in a transition), `collapsedGroups` (group keys: JSON of the value path, e.g. `["EMEA","Ada"]`, empty values `null`) and `aggregates` (the view's `{ key: fn | null }`; `resolveAggregates({ columns, aggregates })` lays them over the column `aggregate` defaults). `viewKeys: ['group', 'collapsedGroups', 'aggregates']`. `api.grouping` is `{ levels, tree: { groups, groupsByKey, leaves }, groupIndices, aggregateFns }` while grouped, else null. Group header rows (`GroupRow`, `rowRenderers.group`) use the data row's cell layout, carry `data-group-key` (no `data-row-key`, so row events and selection ignore them) and handle click/keys through `gridHandlers` placed before keyboard's. One `bodyOverlay` (`StickyGroupRow`) shows the current group header, found by binary search over `groupIndices` (item tops from `rowOffsets` when heights differ); the push-up is a transform written on scroll. The summary footer should read `state.aggregates` through `resolveAggregates` (the key is claimed, so it is not in `viewPassthrough`). In server mode `useGrouping` returns no `rows`: serverData's items already hold the server's groups in the same shape (see Server mode).

## Shared column core

`core/normalizeColumns.js`, `getCellRenderer.js`, `createComparator.js`, `compileCondition.js` and `getExportValue.js` are the integration points for `@lowdefy/blocks-antd/table/`. They hold minimal local stand-ins (text cells, a basic comparator) and will re-export the shared implementations. Renderer contract: `CellRenderer({ value, row, rowKey, column, methods, components, onEvent })`; `onEvent({ name, event })` fires a block event with `{ row, rowKey }` added.

## Editing, TableInput and clipboard

- **Editing** (`features/editing/`, before selection/keyboard/events in the registry). Cells stay tier 0 and know nothing about editing: one `EditingLayer` (rendered in `regions.bottom`) portals the single open editor and the status markers into the rendered cell elements, found by row key and column key; `useGridFeature` re-syncs them after every grid render, so a cell that scrolls back in gets its editor or marker again. Editors (`CellEditor.js`, lazy chunk) come from the column type; per-column edit specs (`createEditSpecs`) compile `editable: { when }`, `validate` and `required` with the shared `compileCondition` and read `required` / `default` from the raw column config.
- **Table saves through events**: `onCellEdit` and `onRowMove` are awaited. The change shows at once as an overlay over `data` (cell overlay keyed `rowKey + columnKey`, move overlay for the order), marked saving; `getEventError` reads the result (`success: false` → `error.error.message`); success keeps the overlay until the row (cell) or `data` (move) changes, failure reverts and shows an error marker with the message. `data` is never written.
- **TableInput** (`blocks/TableInput/`) is `TableRoot` with an `input = { changes, methods }` prop. Its block value is a changeset over `data` — `{ updated: { [rowKey]: { [field]: value } }, added: [{ rowKey, ...row }], removed: [rowKey], moved?, order? }` — never the rows, so large tables keep a small Lowdefy state. `useRows` shows `data` with the changeset applied (`applyChanges`, touched rows only get new identity); edits, adds, deletes, moves and pastes are pure changeset functions written with one `setValue` each (`writeChanges`), with a bounded undo stack of changeset snapshots. Its UI state (view, selection) is React state inside `TableInputRoot`.
- **Row moves** (`rowDrag`, both blocks): `computeRowMove` gives the neighbours, the key order and, with `positionField`, one fractional position (midpoint, ends ∓1024, renumber in steps of 1024 below a 1e-6 gap). Moves are blocked (with the reason as the handle's tooltip) while sorted by anything but the position field ascending, filtered or grouped.
- **Clipboard** (`features/clipboard/`): Ctrl/Cmd+C copies the selected rows or the focused cell as TSV of displayed text (`getExportValue` formatted); TableInput reads Ctrl/Cmd+V from the `paste` event on the root and plans the paste by row key (`planPaste`: coercion per type, skipped cells reported).
- Inline validation is the table's own: Lowdefy block validation (`validate` / `required` on the block) runs engine-side on the value with operators, and blocks cannot report validation errors to it. A TableInput form can validate its changes with operators on the value; cells failing `validate` / `required` are marked in the table.

## Not done yet

- Server mode: open server groups are not part of the value; lazy children of server trees are not supported (trees are client mode).
- Expandable rows render HTML only; Lowdefy blocks in detail rows need engine support.

- `empty` area: input blocks receive no slots (`client/src/block/CategorySwitch.js` renders `input` blocks without `content`); supporting it means the `input-container` category or a slot mechanism for input blocks. `emptyText` covers the common case.
- Header groups (`children`) normalise but render as leaf headers only.
- Hovering a row with `rowLink` does not show the URL (rows are not anchors).
- Sorted tables re-sort fully on a data change (incremental re-sort comes with P3 transactions).
- Text sort keys are built in slices on the header click; a sort set through the value or `defaultView` builds them synchronously in the render.
