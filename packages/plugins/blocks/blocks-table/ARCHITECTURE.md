# blocks-table architecture

`Table` is an input block with slots (category `input-container`: `toolbarStart`, `toolbarEnd`, `bulkActions`, `empty`) whose value is its UI state, `{ view, selected, expanded }` (design D2, D6). This note is for whoever adds the next feature module. Design: `lowdefy-design/designs/table/design.md`. Benchmarks: `bench/RESULTS.md`.

## Layers

```
blocks/Table/Table.js         createLazyBlock wrapper: meta, the skeleton fallback (TableFallback), method proxies
blocks/Table/Table.lazy.js    the implementation chunk (TanStack Table + Virtual + everything below)
core/TableRoot.js             config, data, table state, TanStack instance, block-level feature hooks
core/Grid.js                  the window component: layout, scroll-driven state, grid-level hooks, DOM
core/Body.js, Row.js, Cell.js rows of the current range, memoised by row key and row object
core/HeaderRow.js             header group rows (GroupHeaderRow) and the leaf header row
core/SummaryRow.js            the sticky summary footer (aggregates from core/useSummary.js)
features/<name>/              feature modules, composed through features/index.js
```

Scrolling renders `Grid` and never `TableRoot`, so the engine and the block's own props are untouched by scroll (D10.2).

## State and value

- One React state object (`useTableState`) holds every slice: TanStack's (`sorting`, `columnSizing`, `columnOrder`, `columnPinning`, `columnVisibility`, `rowSelection`), feature-owned non-TanStack slices (`selectionMode`, `density`, `filter`, `search`, `grouping`, `collapsedGroups`, `aggregates`, `expanded` from the expansion module), and the core's (`viewPassthrough`). TanStack is controlled with it (`state` plus generated `on<Slice>Change` handlers), so TanStack APIs such as `column.toggleSorting` and `row.toggleSelected` go through the same path.
- A change goes through `api.updateSlice(name, updater, { cause })`. It records a pending cause; after the change commits, the value is derived (`deriveValue`) and written once with `methods.setValue`, then `onChange { value, cause }` and each feature's `onCommit` fire. Drags and scroll never call it until the gesture ends.
- A slice with `transition: true` (sorting) updates inside `startTransition`: the click paints at once and the table is dimmed (`data-pending`) until the new order lands.
- A value changed from outside (SetState, Reset) re-initialises the state. SetState on a path mutates the object the table wrote, so the comparison is JSON for `view` and identity for `selected` / `expanded` (`getValueSignature`). A null value (mount, Reset) is filled with the resolved default value, without `onChange`. On mount only, a null value first asks the features' `mountValue` (the persisted view, then the active saved view); Reset always returns to `defaultView`.
- `api.loadValue(value, { cause })` replaces the whole state from a value and commits it with that cause (a saved view loading). `api.getValue()` derives the current value; `api.resolveValue(value)` derives the value a state built from `value` would write (the fallback rules applied), which is how a partial saved view is compared with the current one.
- Resolution rules (`createInitialState`, `resolveViewColumns`, `pickViewPart`): each top-level view part falls back value → `defaultView` → column defaults. Unknown view column keys are dropped. Declared columns missing from a stored `view.columns` are appended hidden; `defaultView.columns` entries merge over the column defaults and unlisted columns keep their defaults. A derived view leaves `columns` out while it still equals the configured layout, so columns added to config (or loaded from a request) keep showing up until the user changes the layout.

## Data path

One pipeline in `TableRoot`, each stage a set of feature hooks run in registry order (`features/index.js`):

| Stage           | Hook / code                         | Input → output                                                    | Modules (in order)                                                                                                                           |
| --------------- | ----------------------------------- | ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. source       | `useData(ctx)` (`useFeatureData`)   | `properties.data` (or `[]`) → source rows                         | serverData (the block cache's loaded rows), tree (flattens `childrenField` rows)                                                             |
| 2. key diff     | `stabilizeData`                     | source rows → rows whose identity only changes with their content | core                                                                                                                                         |
| 3. row overlays | `useRows(ctx)` (`useFeatureRows`)   | stable rows → the rows TanStack sees                              | transactions (`applyTransaction` overlay), editing (Table's optimistic overlay, TableInput's changeset)                                      |
| 4. row model    | TanStack                            | rows → `table.getRowModel().rows` (filtered, sorted)              | sorting, filtering (manual in server mode), selection                                                                                        |
| 5. display list | `useItems(ctx)` (`useFeatureItems`) | row model rows → display items, `dataRows`, height estimates      | serverData (rows, server groups, holes), grouping (client groups), tree (tree rows), expandable (detail rows), pagination (the current page) |
| 6. window       | Grid, virtualization                | display items → row offsets and the rendered range                | virtualization (`useRowOffsets`, `useScrollWindow`), serverRange (loads the blocks behind the range)                                         |

- Stage 1 hooks see raw rows: `properties.data` is often a new array of new objects after every engine update. Stage 3 hooks see rows diffed by key (positional fast path, `rowVersionField` or structural compare), so they can hold state on row identity: an overlay entry applies until its row is a different object. Transactions come before editing so an optimistic edit shows over pushed changes, and a pushed change to an edited row settles the edit.
- TanStack uses `createStableCoreRowModel` (reuses `Row` instances; one changed row patches one row) and `createIndexSortedRowModel` (typed `Float64Array` keys per column, index sort, keys cached per rows array; big text columns build their keys in time slices before the sort applies).
- Sort keys come from the shared core: `createSortKeyGetter({ column })` gives each value's typed key once per distinct value, and text keys are ranked with `compareSortKeys`, the comparison `createComparator` itself uses. The index sort therefore orders rows exactly as `createComparator({ column, desc })` (and TableLight) does, empty values last in both directions; `features/sorting/buildSortKeys.test.js` checks this for every type family.
- Rows re-render only when their row object, display index, selection, active column or the visible column list changes.
- Every hook returns its input (the same array, or null from `useItems`) when it has nothing to change, which keeps the memos downstream warm.
- Filtering (stage 4, `createConditionFilteredRowModel`): writes go through one action, `applyFiltering({ filter, search })`: it tests every row in time slices (`prepareFilterResult`, one `Uint8Array` flag per row, cached per rows array and filter context), then sets the `filter` / `search` slices in a transition; the filtered row model finds the prepared flags and only gathers the kept rows. A filter set through the value (SetState, `defaultView`) is tested in the row model itself. Conditions compile once per change with the shared `compileCondition` (compiled field accessors, keyed `in` / `eq` sets); search matches every word against the lowercased display text (`getCellText`) of the searched columns (`searchable: true` ones when any column declares it), cached per row object, and a search that extends the previous one only tests the rows it kept. Incomplete conditions (a leaf without its value, as the filter builder writes it while editing) are pruned before compiling. In server mode (`config.server`, `isServerMode`) TanStack's `manualFiltering` passes the rows through and only the state changes. Trees are flattened before TanStack, so the filter tests every node and the tree's display list keeps the ancestors of the rows it kept.
- Sorting builds its keys for the core rows and reads a filtered subset through `row.index`, so a filter change never rebuilds a column's keys.

### The display list

What the window renders (`api.rows`, Grid's `rows`) is one flat list. Without a `useItems` hook changing it, it is TanStack's row model rows. Entries:

- a TanStack `Row` (a data row),
- a wrapped data row `{ kind: 'row', id, original, row, index, depth?, hasChildren?, expanded?, parentId?, expandable?, detailExpanded? }` (tree rows, expandable rows); Row renders the features' `cellLead` components in its first data cell and sets `aria-level` / `aria-expanded`,
- a group header `{ kind: 'group', key, depth, columnKey, value, empty, count, aggregates, collapsed, ... }`. Client groups (`flattenGroups`) add their leaf range `start`, `end`; server groups (`buildServerItems`) add `groupPath` (the values naming the group's own list) and start collapsed. `key` is the JSON of the group's value path. Both render with grouping's `GroupRow` and the sticky `StickyGroupRow`, and toggle through grouping's `toggleGroup` (server mode: `api.serverStore.toggleGroup`),
- a detail row `{ kind: 'detail', key, parentId, original }` (expandable),
- `undefined`: a server row that is not loaded yet, rendered as a `SkeletonRow`,
- a skeleton child `{ kind: 'skeleton', key, depth }` (tree: a lazy row's children while they load), also a `SkeletonRow`, indented,
- a server error row `{ kind: 'error', key, listKey, groupPath, index }` (a failed block, `ServerErrorRow` with Retry).

`core/isDataItem.js` tells data rows from the rest; code that walks `api.rows` for data rows uses it. `api.dataRows` is the view's data rows in display order, every page: the first hook's `dataRows` (grouping: the leaves, including rows of collapsed groups; pagination: the data items of every page), else the list's data items. Export reads it. Pagination (`pagination: true`, client data only) is the last `useItems` hook: a page is a slice of the finished display list (group headers and rows when grouped), and its pager is a `regions.bottom` fragment that reads `api.page`; `useFeatureItems` runs before `useFeatureFragments` so the pager renders with the same list. `Body` renders a non-row item with its feature's `rowRenderers[kind]`, with the same props as `Row` plus `item` and `layout`.

Row heights (D10.1): one mechanism, `features/virtualization/useRowOffsets.js`, serves fixed rows, measured rows and detail rows. Every item is one row high (the density, or `rowHeight`) unless it is measured: data rows when a visible column wraps or clamps to more than one line (`isMeasuredColumn`; column virtualisation is then off, as a row's height depends on every cell), and items a `useItems` hook returns a `rowHeights(item, index)` estimate for (expandable detail rows, estimated at three rows). Measured elements carry `data-measure-key` (`getMeasureKey`: the row id, or `kind:key`) and the body reports their rendered heights after each window render (`api.measureRows`; a detail row also reports when its content resizes). Heights are cached by key and dropped on a layout change; items that grew above the viewport shift the scroll position by the same amount. With any measured item the offsets (`computeRowOffsets`, item tops, length n + 1; a measurement shifts them from its first changed item with `shiftRowOffsets` instead of recomputing, and the measurements before a render share one copy) are `api.rowOffsets`, and `computeWindow`, the body height, `scrollToCell` and the sticky group header use them instead of `index * rowHeight`; TanStack Virtual's per-row positioning is off then. The rendered range is clamped to the list in the render where the list shrinks (`useScrollWindow`), before the layout effect catches up.

## Server mode (D9)

`features/serverData`. `data: { mode: server, request, blockSize, maxBlocks }` registers the internal event `__tableFetch` (a Request action for `data.request`) and fetches with `{ startRow, endRow, view: { sort, filter, search, group, aggregates }, groupPath, selected }`; `view.aggregates` is the aggregates in effect (the view's over the columns' `aggregate` defaults). `createServerStore` owns:

- a `createBlockCache` per view: blocks of `blockSize` rows per list (the root list `[]` and each expanded group's list, keyed by `JSON.stringify(groupPath)`), LRU-evicted beyond `maxBlocks` loaded blocks, never evicting a visible or loading block. `invalidate()` bumps a generation: responses that started before are ignored (triggerEvent cannot be aborted) and invalidated blocks stay on screen until they reload.
- the view: `useServerView` derives it with `deriveValue`, so it follows whichever module owns sort, filter, search or group. A new view gets a new cache, scrolls to the top, fetches block 0, and keeps the previous cache on screen (`pending`, dimmed) until the new root block lands; responses for a superseded view's cache are ignored.
- loading: `serverRange` (grid level, after virtualisation) hands every rendered range to `onRange`. Slow range changes load the missing blocks at once; fast ones (above 0.05 rows/ms, about 2000px/s) wait until the range settles for 120ms. A block landing re-renders with the same range and never cuts a pending settle short.
- the display list (`buildServerItems`): the root list's rows, or its groups with expanded groups followed by their own list, with `undefined` holes for unloaded rows (an expanded group's leaf list has its group's `count` of holes until its first block lands, and the group item is `loading`: a spinner in its chevron). A failed block is one error item in place of its rows; `store.retry` reloads only it, and loaded rows stay. `isRefreshing()` (loaded blocks reloading after `refresh`) is the `refreshing` fragment: the progress bar, no dimming. `segments` map item runs to list rows, which is how a range maps to blocks (`getNeededBlocks`). `total` from the responses sizes the lists, the scroll height and `aria-rowcount`. Group rows carry the response's `count` and `aggregates`; the root list's `aggregates` are `api.serverStore.getAggregates()` (for the summary footer). Client grouping adds no rows in server mode; it only provides `api.grouping` (levels, aggregate functions, the group indices of the server list) for the group rows.
- open server groups live in the store (`toggleGroup`, `collapseAllGroups`), not in the value, and reset when `view.group` changes. Server groups have no group checkbox (their rows are not in the browser).

TanStack sees only the loaded leaf rows (`manualSorting`/`manualFiltering`/`manualGrouping`), for selection, row lookup and events. Selection is always preserved in server mode; the header checkbox writes `{ all: true, except: [], filter, search }` (`selectionMode: 'all'`, the filter and search in the `selectionView` slice), and `api.selectionExcept` remembers exceptions whose rows were evicted. `exportCsv` fires `onExport { view }`. `refresh()` invalidates the cache; `applyTransaction` merges updates into loaded rows and refetches the visible rows for adds and removes. Row moves are blocked in server mode.

## Trees and expandable rows

`features/expansion` owns the `expanded` slice (row keys, the value's `expanded`) and `toggleRowExpanded` (fires `onRowExpand`; a lazy expand with `needsChildren` is awaited through `api.childLoads`, which the tree's display list subscribes to: the row is `loading` with a skeleton child while the event runs, and a failure collapses it with its `error` on the chevron); tree rows and expandable rows both read it. `features/tree` (client mode only) flattens `childrenField` rows in `useData`, builds the parent/children index from the core rows (`parentField` links rows to the row with that key; missing parents and cycles make roots) and the display list from the row model rows in `useItems`: siblings keep the row model order (so a sort sorts within levels) and ancestors the filter left out are kept, placed before their first descendant. `api.tree` gives `rowSelection.cascade` and Right/Left their descendants and parents. A tree is never grouped (grouping stays inactive and offers no header menu entry) and its rows cannot be moved. The scroller's role is `treegrid`. `features/expandable` wraps rows with their expand state and adds a `detail` item after expanded rows; `DetailRow` renders `expandable.template` (nunjucks, compiled once in `useTableConfig`) through `renderHtml` and measures itself.

## Loading states (D17)

The shared pieces live in `@lowdefy/blocks-antd/table/` (TableLight uses them too): `resolveLoadingState`, `holdRows` / `useHeldRows`, `getSkeletonPhase` / `useSkeletonTiming`, `getSkeletonShape`, `getSkeletonWidth`, `getSkeletonRowCount`, `SkeletonCell`, `LoadingAnnouncer` and `tableLoading.css`.

- `TableRoot` takes the loading signal (`loading` prop or `properties.loading`), holds the last rows while it is true and `data` has none (stage 1 reads the held rows), and resolves the state from it, the server fragments (`loading`, `pending`, `refreshing`) and the transition's `isPending`, with `sourceCount` the rows after stage 3 and `displayCount` the display list. `api.loadingState` is `initial` while the skeleton shows (Export, select all and the bulk bar read it).
- `Grid` renders `SkeletonRows` in place of the body while the skeleton shows (initial, or holding its 300 ms minimum), else the body, else `EmptyState` (filtered: "No matching rows" and Clear filters, which calls `applyFiltering({ filter: null, search: null })`). Root attributes carry the rest: `data-loading-state`, `data-skeleton-hidden` (the first 120 ms), `data-busy` (refetch, refresh), `data-pending` (view change). CSS shows the header's progress bar for busy or pending and dims the body 300 ms into pending; neither needs a render. The scroller is `aria-busy` while any of them holds; `LoadingAnnouncer` is a polite live region.
- `TableFallback` is the same initial state without the engine: `computeFallbackLayout` feeds the column config (through `resolveViewColumns`) and the leading columns into `buildLayout`, the layout core `computeLayout` also uses, and it renders `HeaderRow` (sort indicators only), `SkeletonRows` and placeholders for the toolbar, pager and add-row rows. `useSkeletonTiming` keeps its start time per block id, so the table continues the fallback's timing.
- Popovers and editors that load on first use fall back to `PopoverLoading` (an open antd Popover with a spinner at the real popover's anchor) or a spinner, never `null`.
- The template compiler (`@lowdefy/nunjucks`) loads only when `needsTemplates` says the config uses one; `useTableConfig` calls `readTemplateCompiler`, which suspends until it has loaded, and passes it to `compileColumns` and `normalizeExpandable` as `compileTemplate`.

## Layout contract

`computeLayout` (TanStack's visible columns through `buildLayout`) returns the visual column order (`start` = leading columns + start-pinned, `center`, `end`) with widths, sticky offsets, centre prefix offsets, and CSS variables on the root: `--lf-w<n>` (width of layout column `n`), `--lf-l<n>` / `--lf-r<n>` (sticky offsets), `--lf-total`, `--lf-center-w`; the scroller carries `--lf-center-before` (the column-virtualisation spacer). Cells use the column's shared `style` object. `api.previewLayout({ widths })` recomputes and writes the variables without rendering: use it for any drag. The scroll range update (`useScrollWindow`) also writes `data-scrolled-start` / `data-scrolled-end` on the scroller when they change (`writeScrollEdges`), from which the pinned edge cells cast their shadow; no row renders for it.

## Feature module

A module is a plain object exported from `features/<name>/<name>Feature.js` and listed in `features/index.js`. Order matters: it is the order of handlers and hooks. Every field is optional.

**Feature sets and optional features.** A table renders with its own feature set (`core/useFeatureSet.js` → `TableRoot`'s `features` → `api.features`): the list plus what the core collects from it once (`createFeatureSet`: header parts, grid handlers, slices, claimed view keys, row renderers, cell leads, body overlays, the stable TanStack feature set). Core code reads `api.features`, never the registry. Registry entries made with `optional({ name, needs, load, methods })` load in their own chunk only when `needs({ properties, content, input, rowWindowStrategy })` is true: editing (TableInput, an editable column or `rowDrag`), paste (TableInput), serverData and serverRange (`data` is an object), groupRows (a groupable column), tree, expandable, views (`persist`, a `views` key, or the toolbar's view tabs), toolbar (configured, a toolbar slot with blocks, or `importCsv`), enrichment and newRows (`needsEnrichment`: an enrichment, ai or extract column, a `status` column, a `userDefined` column, `providers`, `addColumn`, `addRow` or `importCsv`; formula columns alone do not load it, the shared column core reads them) and positionedRows (the bench-only strategy). A table keeps the optional features it has loaded (a ref in `useFeatureSet`): config that passes through a smaller state, such as columns read again by a request (empty while it loads), must not remount it and drop its UI state and pushed rows; every feature works without its config. Until the needed chunks have loaded, `useFeatureSet` suspends, so the lazy block keeps its fallback and registers methods only once the whole table is there; `Table.lazy.js` keys `TableRoot` on the set's signature, so a config that needs a different set remounts the table. A table that does not load an optional feature gets a stand-in with its declared block `methods` as no-ops. State an optional feature reads but the value must keep either way stays in an always-on module: grouping's slices (`group`, `collapsedGroups`, `aggregates`) are `groupingFeature`, its rows and handlers `groupRowsFeature`. Popovers and menus that open on demand are `lazyComponent`s in Suspense boundaries of their own, preloaded on hover or focus of their trigger: the column filter popover, the toolbar's filter builder, the column manager, the header menu dropdown, the cell editor, and enrichment's column picker (the "+" header, a user column's header menu), cell details panel (a details cell) and CSV import dialog (the Import button). `pnpm bench --chunk` reports the main chunk (the entry and what it imports statically) by module group and every on-demand chunk.

`api` (`core/createApi.js`) is one stable object per table, refreshed every render: `table`, `config`, `properties`, `value`, `content` (the block's slots), `state`, `layout`, `rows`, `dataRows`, `rowHeight`, `rowOffsets`, `measureRows`, `footerHeight`, `page`, `headerHeight`, `rootRef`, `scrollerRef`, `methods`, `components`, `updateSlice`, `setSliceSilently`, `loadValue`, `getValue`, `resolveValue`, `previewLayout`, `actions`, `keyboard`, `views`, `suppressClick()` / `takeSuppressedClick()` (a drag that ends on a header must not also sort). `api.total`, set by server mode (`api.serverStore.getRecordCount()`, the root `total`, or the sum of the root groups' counts when grouped), is the record count the toolbar and bulk bar show; client-side it is the filtered row count (`core/getRecordCount.js`).

DOM contract for handlers: body rows carry `data-row-key` (TanStack row id = `String(rowKey)`) and `data-row-index` (display index; the header row is `-1`); group header rows carry `data-group-key` instead of `data-row-key`; cells carry `data-lf-cell`, `data-col-key`, `data-col-index` (layout index) and the class `lf-table-gridcell`; header cells `data-lf-header`; header group cells `data-group` (no `data-lf-cell`, so keyboard navigation skips them); special columns `data-special`. Body rows carry `lf-table-row`, the class the shared cell CSS reveals `showOn: hover` buttons from (a row element holds its pinned cells too, so CSS hover covers the whole row and no `data-row-hover` tracking is needed).

## Adding the planned modules

- **headerMenu** (built): `headerParts` (menu button laid over the end of the header cell on hover or focus, so it takes no room from the title; tabbable while its header cell is active; antd `Dropdown` mounted only while open, anchored to a zero-height span on the header's bottom edge), `gridHandlers` click/pointerdown/keydown placed before sorting and ordering (the button never sorts or starts a drag; Alt+ArrowDown, Shift+F10 or the context menu key on a header opens the menu), and its own `headerMenuItems` (sort, pin, freeze up to here, autosize, hide). Other features add items through `headerMenuItems`.
- **filtering** (built): the filtered row model slot, slices `filter` and `search` (`transition: true`), `viewKeys: ['filter', 'search']`, `applyFiltering` (above), the column filter popover (`FilterIndicator` header part, simple editors per type or the `FilterBuilder` limited to the column) and `FilterBuilder` (`src/features/filtering/FilterBuilder.js`, props `{ condition, columns, user, onChange }`: nested And/Or groups three levels deep, operators from `getOperators`, value editors per type; it keeps its own state, so a caller writing through a transition can pass the committed condition back). Methods `setFilter`, `clearFilters`, `setSearch`.
- **columnManager** (built): a popover in `regions.top` listing every declared column (visible in table order with the start/end pinned boundaries, then hidden), search, visibility checkboxes, drag handles (HTML5 drag, or Alt+ArrowUp/Down on a handle; a column dragged across a boundary is pinned or unpinned, a boundary can be dragged too) and "Reset to default". Each checkbox, drop and reset is one `columns` change. A column with an empty title (an actions column, `title: ''`) is listed by its humanized key (`getPlainTitle`, also used by the filter and toolbar lists), so it can still be hidden and moved; the list takes the viewport height below the popover's anchor (`getListRoom`), snapped to the last whole entry (`snapListHeight`), and fades at an edge while entries are out of view that way (`updateScrollHints`). Method `openColumnManager`.
- **density** (built): the `density` and `wrap` slices and view keys; density starts from `size` (`config.defaultDensity`); the toolbar toggles are `updateSlice('density')` and `updateSlice('wrap')`. With `view.wrap`, `computeLayout` gives text-like columns without their own `wrap`/`ellipsis` a wrapped copy (`getViewWrapColumn`, the shared `getCellLayout` class), so their cells wrap and their rows are measured. Pagination owns the `pageSize` slice (`view.pageSize`, else the property).
- **toolbar** (built, `features/toolbar/`): off by default; `config.toolbar` is `normalizeToolbar(properties.toolbar)` (quick filter keys validated against the columns). `useFeature` returns `regions.top` (also shown for blocks in the `toolbarStart` / `toolbarEnd` slots alone). It owns no state: search calls `actions.setSearch`, the Filter popover (`filtering/FilterBuilder.js`) and quick filters (an `in` leaf per chip, ANDed at the root) write through `actions.applyFiltering`, sort `updateSlice('sorting')`, group `actions.setGroupKeys`, Columns `actions.openColumnManager`, non-enum chips `actions.openColumnFilter({ key })`, Export `actions.exportCsv`. The record count is `getRecordCount`. `gridHandlers.keydown` maps Cmd/Ctrl+F to the search box. Filter, Sort and Group show their count inside the button (`ToolbarCount`); Sort counts only a sort that differs from `defaultView`'s (`isDefaultSorting`).
- **views** (built, `features/views/`): saved views and `persist`. `mountValue` supplies the persisted view (sanitized: unknown keys dropped, missing declared columns appended hidden), else the active saved view. `useViews` keeps the active view id (block UI state, following `activeView`), compares the current view with the active saved view resolved through `api.resolveValue` (`isViewDirty`: search and collapsed groups never make a view dirty), exposes `api.views` (`select`, `save`, `saveAs`, `discard`, `remove`) and writes the persisted payload `{ view: compactView(...), activeView }` after each view change (localStorage key `lowdefy-table:<key>`, or a base64url query parameter with `history.replaceState`). `onViewSelect` fires from `onCommit` after the loaded view commits.
- **bulk** (built): `regions.bottom` bar while rows are selected, with the `bulkActions` slot; `selectAllMatching` (action and method) selects the view's data rows in `selectionMode: 'all'`, written as `{ all: true, except, filter, search }` (counted against `api.total` in server mode). The value describes itself so a request can resolve it; new rows join it only if they match (client: the filtered rows), and a filter or search change clears it (`useSelection`, `isSelectionViewCurrent`).
- **enrichment** (built, `features/enrichment/`, design `code-docs/plans/enrichment-tables.md`): column kinds come from the shared core (`normalizeColumnKind`, `linkColumnKinds`: enrichment and ai columns read `_enrich.<key>.value`, their run state from `_enrich.<key>`, and `inputSources`; formula columns get `column.read`, which every value reader uses through `readColumnValue` / `core/createColumnAccessor.js`; extract columns a field into the source's `raw`). `Cell` renders columns with a `stateField` through `EnrichmentCell` (tier 0: queued, running, value, error with a hover-mounted tooltip, empty; stale when `hashEnrichmentInputs(resolveEnrichmentInputs(...))` differs from `inputHash`). `useEnrichment` owns the UI state (`api.enrichment.ui`), the raw column configs event payloads carry, the header chips' counts (loaded rows, or server `aggregates[key]` counts) and the trailing column ("+" header, row run buttons). The module is optional (its own chunk, with newRows; see Feature sets and optional features) and reaches the core only through extension points: `cellRenderer` (EnrichmentCell for columns with a `stateField`), `headerParts`, `headerMenuItems`, `toolbarItems` (ImportButton), `bulkItems` (RunSelectedButton) and `gridHandlers` (click, keydown, and pointerover / focus to preload overlays); `config.enrichment` (`normalizeEnrichment`, small) stays in the config the core builds. Overlays (LazyColumnPicker, LazyCellDetails, LazyImportDialog: `lazyComponent`s in chunks of their own, preloaded on hover or focus of what opens them; the delete confirmation) mount only while open, in `regions.bottom` with Table's "+ New row". Header menu items (Run submenu, Rename/Edit/Duplicate/Insert/Delete for `userDefined` columns) show when the table has the event they fire. `newRowsFeature` (after editing) appends the optimistic new rows (`api.savingRows`, `data-saving`). Running spinners pause while the grid scrolls (`usePauseWhileScrolling`). Everything saves through awaited events: onColumnAdd, onColumnUpdate, onColumnDelete, onColumnRun, onRowRun, onCellRun, onRowAdd, onImport. Queued cells with `waitingFor` (waiting for a column they read) show "Waiting". Error columns (a `userDefined` column whose config is invalid, `invalid` from the shared core's `invalidateColumn`) render through the same `cellRenderer` as "Invalid column: <reason>", with `InvalidMark` in the header, `data-lf-invalid` on it (`headerCellProps`) and only Edit column and Delete column in the menu (the picker edits the kind the raw config asked for, `getDraftKind`). `inputFieldPrefix` gives new input columns (picker, CSV import) their `field` (`getInputField`), so onRowAdd and onImport values are all at field paths. The picker offers AI answer types `AI_OUTPUT_TYPES` (text, number, boolean, tag, tags) and refuses templates that are more than placeholders (`findTemplateProblem`).
- **queue** (built): single-key row actions (`gridHandlers.keydown` before keyboard's, after editing's; a bare key on a focused cell fires the first shown, enabled button or menu item with that `key`, with its click payload) and `keyboard.next` (`actions.afterRowAction`, also called by `api.onCellEvent` for button and menu events: once the event's actions resolve, focus moves to the data row that followed).
- **grouping** (built, `features/grouping/`): not TanStack's grouping, whose grouped model runs before sorting. `useGrouping` (a `useItems` hook) takes the sorted row model (after filtering, before pagination), builds the group tree in one pass (`buildGroupTree`: counts, leaf ranges and per-group aggregates with the shared `computeAggregate`), and flattens it (`flattenGroups`) into the display list; collapsing reruns only the flatten. Slices `grouping` (column keys, in a transition), `collapsedGroups` (group keys: JSON of the value path, e.g. `["EMEA","Ada"]`, empty values `null`) and `aggregates` (the view's `{ key: fn | null }`; `resolveAggregates({ columns, aggregates })` lays them over the column `aggregate` defaults). `viewKeys: ['group', 'collapsedGroups', 'aggregates']`. `api.grouping` is `{ levels, tree: { groups, groupsByKey, leaves }, groupIndices, aggregateFns }` while grouped, else null. Group header rows (`GroupRow`, `rowRenderers.group`) use the data row's cell layout, carry `data-group-key` (no `data-row-key`, so row events and selection ignore them) and handle click/keys through `gridHandlers` placed before keyboard's. One `bodyOverlay` (`StickyGroupRow`) shows the current group header of each level, stacked outermost first (`getStickyGroups`: per level a binary search over that level's header indices from `buildStickyLevels`, item tops from `rowOffsets` when heights differ); each level's push-up is a transform written on scroll, and a new outer group pushes the inner levels out first. A toggle from an inner sticky header scrolls that group's header to its own slot (`scrollToCell` `startInset`). The summary footer reads `state.aggregates` through `resolveAggregates` (the key is claimed, so it is not in `viewPassthrough`), so it shows for view aggregates alone too. In server mode `useGrouping` returns no `rows`: serverData's items already hold the server's groups in the same shape (see Server mode).

## Shared column core

Columns, cells, conditions and exports come from `@lowdefy/blocks-antd/table/<file>.js`, the core TableLight renders with, so a TableLight config means the same thing on Table (TableLight is a strict subset of Table's properties):

- `useTableConfig` runs `normalizeColumns` (string or object columns, header tree) and `compileColumns({ columns, columnsByKey, user })` once per config; `rowRules` compile with `compileRules`. `user` is the block property the app sets with `_user`, so `$user` works in client-side conditions (filters, rules, `expandable.rowExpandable`).
- `Cell` renders `renderCell({ column, row, rowKey, methods, components, onEvent })` inside its grid cell, after the row's `cellLead` elements in the first data cell. Renderers build full event payloads (buttons, menus, `onCellLink`) and `api.onCellEvent` passes them to `methods.triggerEvent` unchanged.
- Row events use the shared `isControlTarget` (with the row as container) and `resolveLink`; `rowLink` navigates with `getHtmlEnhancements().link(...)`, the client's registered Link function, as TableLight does. With `onRowClick` defined, a plain click runs it and only a modified click follows the link.
- Export uses `getExportValue` and `htmlToText`; the summary footer uses `computeAggregate` and `getAggregateText` over the aggregates in effect (`resolveAggregates`: the view's over the column defaults, the ones group headers show); in server mode it shows `api.serverStore.getAggregates()`. A summary cell shows the full label, its short form (`core/aggregateShortLabels.js`: Σ, Avg, #, ...) or none, whichever fits beside the value by `api.textMeasure` widths (`getSummaryLabel`), and never cuts a value that fits alone to make room for a label; the title holds the full label and value.
- `tag` / `tags` cells on one line get `renderCell`'s `fit` (`core/getCellFit.js`: the layout column's content width and `api.textMeasure`, canvas text widths cached by text with the styles read once per table from a hidden probe), so they show the chips that fit whole and a +N count, recomputed when the layout column changes (not during a resize drag).
- Rich cell types (`core/lazyCellTypes.js`) render through `core/LazyCell.js`: cells that come into view during a fast scroll show their text (`getCellText`) in the cell layout and upgrade when the scroll settles; `buttons` with `showOn: hover` mount only on the hovered row or the row holding keyboard focus (`:focus-visible`; focus a mouse click leaves on a checkbox or cell does not count). `api.cellActivity` (`core/createCellActivity.js`) holds the hovered row, keyboard-focused row and fast-scroll flag, fed by `features/lazyCells`.
- The engine's own grid-cell class is `lf-table-gridcell` (the shared core owns `lf-table-cell`, `lf-table-empty` and `lf-table-progress`).

## Editing, TableInput and clipboard

- **Editing** (`features/editing/`, before selection/keyboard/events in the registry). Cells stay tier 0 and know nothing about editing: one `EditingLayer` (rendered in `regions.bottom`) portals the single open editor and the status markers into the rendered cell elements, found by row key and column key; `useGridFeature` re-syncs them after every grid render, so a cell that scrolls back in gets its editor or marker again. Editors (`CellEditor.js`, lazy chunk) come from the column type; per-column edit specs (`createEditSpecs`) compile `editable: { when }`, `validate` and `required` with the shared `compileCondition` and read `required` / `default` from the raw column config.
- **Table saves through events**: `onCellEdit` and `onRowMove` are awaited. The change shows at once as an overlay over `data` (cell overlay keyed `rowKey + columnKey`, move overlay for the order), marked saving; `getEventError` reads the result (`success: false` → `error.error.message`); success keeps the overlay until the row (cell) or `data` (move) changes, failure reverts and shows an error marker with the message. `data` is never written.
- **TableInput** (`blocks/TableInput/`) is `TableRoot` with an `input = { changes, methods }` prop. Its block value is a changeset over `data` — `{ updated: { [rowKey]: { [field]: value } }, added: [{ rowKey, ...row }], removed: [rowKey], moved?, order? }` — never the rows, so large tables keep a small Lowdefy state. `useRows` shows `data` with the changeset applied (`applyChanges`, touched rows only get new identity); edits, adds, deletes, moves and pastes are pure changeset functions written with one `setValue` each (`writeChanges`), with a bounded undo stack of changeset snapshots. Its UI state (view, selection) is React state inside `TableInputRoot`.
- **Row moves** (`rowDrag`, both blocks): a drop gap on the page (`api.rows`) maps to a gap in `api.dataRows` (`getDataGap`), so a move stays on its page while its indices, neighbours, key order and positions cover every page; an added row's position follows the last data row. `computeRowMove` gives the neighbours, the key order and, with `positionField`, one fractional position (midpoint, ends ∓1024, renumber in steps of 1024 below a 1e-6 gap). Moves are blocked (with the reason as the handle's tooltip) while sorted by anything but the position field ascending, filtered or grouped.
- **Clipboard** (`features/clipboard/`): Ctrl/Cmd+C copies the selected rows or the focused cell as TSV of displayed text (`getExportValue` formatted); TableInput reads Ctrl/Cmd+V from the `paste` event on the root and plans the paste by row key (`planPaste`: coercion per type, skipped cells reported).
- Inline validation is the table's own: Lowdefy block validation (`validate` / `required` on the block) runs engine-side on the value with operators, and blocks cannot report validation errors to it. A TableInput form can validate its changes with operators on the value; cells failing `validate` / `required` are marked in the table.

## Not done yet

- Server mode: open server groups are not part of the value; lazy children of server trees are not supported (trees are client mode).
- Expandable rows render HTML only; Lowdefy blocks in detail rows need engine support.

- TableInput is still an `input` block without slots (no toolbar or bulk bar slots, no `empty` slot); `emptyText` covers its empty state.
- The first search over many visible columns formats every searched cell (about 4 s for 100k x 50, in slices, without blocking); later searches read the cached text.
- Hovering a row with `rowLink` does not show the URL (rows are not anchors).
- Sorted tables re-sort fully on a data change (incremental re-sort comes with P3 transactions).
- Text sort keys are built in slices on the header click; a sort set through the value or `defaultView` builds them synchronously in the render.
- Pagination (`pagination: true`) keeps the page in local state, not in the value; `scrollToRow` only finds rows on the current page.
- `buttons` cells mount antd `Button`s (the shared renderer, as in TableLight). D4's static token-styled form for always-visible buttons is not built; the fast-scroll placeholder stands in for it.
